## Analytics implementation boundary

Use the existing response names consumed by `ProgressAnalyticsPanel`: `overview`, `challengeStats`, `studentProgress`, `topStudents`, `progressOverTime`, and `difficultyBreakdown`. The UI expects `lastActivity` on student rows; returning only `lastLogin` does not populate that column. `topPerformers` is not the rendering contract.

A read-side PostgreSQL snapshot should join visible catalog exercises and enabled objectives to current completions, time tracking and student identities. Reuse the existing SecureShop retired-launch exclusion from the progress repository. Compute the enabled-objective denominator even when no students exist. Retain distinct, explicitly labeled 30-day activity and 24-hour dashboard windows. Use active accounts with the explicit student role consistently for all analytics populations, rankings, time and activity. Keep the separate management roster able to list inactive students. “This week” means the current UTC calendar week beginning Monday; the timeline covers the current UTC date and preceding 29 dates. A workshop with all enabled objectives completed is not in progress.

Qualification needs dated, nonzero fixtures plus hidden exercises, disabled objectives, inactive students, administrator accounts, and retired SecureShop launches. Test zero-student and zero-objective cases without dividing by zero or hiding the exercise catalog. This design is pending implementation and native qualification.
