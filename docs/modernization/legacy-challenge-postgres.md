# Generic legacy challenge PostgreSQL store

The mounted AI, ecommerce, vulnerability and workshop-mode middleware paths now use `server/database/legacyChallengeStore.js`. It selects native PostgreSQL with `PLATFORM_DATABASE_ENGINE=postgres`; only the explicitly selected legacy branch imports `database/init.js`. Named asynchronous methods preserve the existing callback response envelopes, including insertion IDs and affected-row counts. This facade does not parse or translate SQL.

The separate `legacy_challenge` schema/database and `dvaia_legacy_challenge_runtime` role hold demo users, products, comments, reviews, cart, orders, order items, files, AI conversations and vulnerability settings. They use `LEGACY_CHALLENGE_DATABASE_URL` and `LEGACY_CHALLENGE_MIGRATION_DATABASE_URL`, never identity or SecureShop pools. `initializeLegacyChallengeDb(migrationPool)` runs the native migration and pure demo seed; existing content is retained. There is no automatic import of a working `dvaia.db`.

Raw SQL generated by the educational routes remains raw and exploitable. Queries run with the challenge search path and runtime role, using one PostgreSQL statement per operation. This matches the original sqlite3 `run`/`all` single-statement boundary rather than enabling additional stacked statements. PostgreSQL dialect differences are visible: category binding uses `$1`, order summaries use `STRING_AGG`, and cart uses `INSERT` because the original table had no unique user/product constraint and `INSERT OR REPLACE` therefore also appended rows. User-supplied SQLite/MySQL dialect payloads can fail with PostgreSQL errors. Existing synthetic attack examples that were invalid SQL are not presented as successful exploits or silently rewritten. The route's simulated time-based narrative remains explicitly simulated.

No sanitization, authorization checks, CSRF protection, upload restrictions, command restrictions or SSRF restrictions were added to teaching sinks. Demo user foreign keys are not enforced, matching SQLite's original default foreign-key-disabled connections and preserving arbitrary challenge session IDs. Checkout retains its preexisting separate operations and zero total; this slice does not claim atomic commerce checkout. A subsequent transaction improvement must preserve documented intentional commerce behavior.

Verification: `tests/legacyChallengeStore.test.js` passes two guarded tests, including mounted local HTTP response contracts and no SQLite imports. `tests/postgres/legacyChallenge.integration.test.js` is opt-in on disposable `PG_LEGACY_CHALLENGE_TEST_RUNTIME_URL`/`PG_LEGACY_CHALLENGE_TEST_MIGRATION_URL`; it covers native SQLi, raw stored HTML, conversation access, cart/order operations, isolated permissions and repeated initialization. Its first native run remains pending shared harness provisioning.
