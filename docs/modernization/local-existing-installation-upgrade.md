# Local existing-installation upgrade

This is an operator sequence for a new local PostgreSQL candidate, not an automatic whole-installation transaction. Keep the old application, configuration and source files intact until the candidate passes acceptance. Use private directories and configuration files; commands below use placeholders, not live connection credentials.

1. **Quiesce and inventory.** Stop the old application's writers using its owned launcher control; separately stop any other writer to the source files. Record the old application revision and runtime configuration. Do not reset databases. Inventory external MySQL, uploads, fixed teaching trees, vector sidecars and process memory separately. Old Excessive Agency attendee state held in memory is not contained in a SQLite export.

2. **Export once, preserve the archive.** Run `node db/postgres/export-legacy.js --source-dir /private/source --output /private/new-archive --plan` first, then the same command without `--plan`. Output must be new. The exporter reads the known SQLite files read-only, preserves unknown tables, and rejects active WAL/journal state. Its consistency boundary is one file; quiescence provides the cross-file boundary. Preserve the archive and every subsequent review/report together.

3. **Provision new isolated targets and apply schema migrations only.** Use the named runtime/migration roles and 16 database-variable pairs in `db/postgres/initialize-application.js`. The authoritative list is `requiredStoreManifest`; `./start_all.sh --plan` reports every required runtime/migration pair without connecting to the databases. Do not point these variables at the old installation or run normal fresh-install seeding before import. The existing `migrate(pool, directory)` API in `db/postgres/migrate.js` applies the explicit identity or family migration directory without calling runtime seed functions; family setup must follow its import prerequisites. There is no single schema-only whole-installation operator command. Legacy Sensitive specifically expects its three default documents; SecureShop permits migration-created empty corpus defaults. Verify these prerequisites against the linked family workflow before importing.

4. **Review and apply platform identity first.** Follow [platform archive apply](platform-archive-apply.md), using `npm run db:legacy:plan-platform` to inspect the archive and the reviewed `npm run db:legacy:apply-platform` path. Its default is a constraint dry run; add `--apply` only for the new target. Resolve every missing category, normalization, retained table, timestamp and solution conflict explicitly. Save the immutable archive-bound identity map. Never infer identity continuity from equal numeric IDs. Historical completions remain historical imports, not fabricated Judge passes. Old session tokens do not become current authenticated sessions: users log in again.

5. **Apply each supported family to its own target.** Follow [workshop archive operator](workshop-archive-operator.md) for `npm run db:legacy:apply-workshop -- --archive /private/new-archive --family FAMILY --review /private/FAMILY.json`, first dry run and then `--apply`. Supported families are `mcp`, `csrf`, `xss`, `ctf`, `finflow` and `supply_chain`. Supply the exact persisted platform `ownerBinding` and reviewed opaque-owner resolutions. Keep all candidate writes stopped during cross-database identity checks. ARIA/NOVA use `node db/postgres/import-workshop-archive.js --archive /private/new-archive --family aria|nova --review /private/family.json --database-env SQL_WORKSHOP_MIGRATION_DATABASE_URL` (use the NOVA variable for NOVA), with `--apply` only after dry-run success. Their exact envelope is `{family, naiveTimestamps, review:{archiveDigest, retainedOtherSources}, ownerBinding, opaqueOwnerResolutions}`; `IDENTITY_MIGRATION_DATABASE_URL` verifies the persisted platform binding before target import. Do not reuse an earlier unbound import command.

6. **Apply generic, legacy-sensitive and SecureShop stores.** Follow [active-store operator](active-archive-operator.md). `npm run db:legacy:plan-active -- --archive /private/new-archive --target TARGET` emits a proposal; inspect it and save `reviewEnvelope`, not the whole plan report, as the reviewed input. Dry-run/apply `legacy_challenge`, `legacy_sensitive`, `secureshop` and `secureshop_agents` individually. Apply SecureShop commerce before agents. These commits are separate; a failed second store does not roll back the first. Preserve unsupported sources and table namespaces archive-only instead of merging by similar names.

7. **Restore and verify assets before candidate activation.** Follow the active-store asset section for explicit bundles, reference hashes and new staging roots. Database commit alone does not activate a path. SecureShop's `npm run db:legacy:verify-secureshop-assets -- --archive … --review … --restore … --base-url … --receipt …` verifies the staged application mapping after it is configured. Opaque attachment content is not exhaustive file discovery. Check fixed teaching trees before restoration with `node db/postgres/fixed-tree-assets.js --bundle DIR --manifest-digest SHA --candidate DIR --candidate-stopped --candidate-is-staged`. No review emits a hash-bound plan; add `--review FILE` for validation and `--apply --operation-root NEW_DIR` only after resolving collisions. `--include-finflow` explicitly includes that tree. Differing files require exact source/candidate hash decisions; partial failure leaves `COPY_INCOMPLETE`, not an activation receipt. The tool reports `applicationActivated:false` and `crossFileAtomic:false`; see [fixed-tree asset migration](fixed-tree-asset-migration.md). Imported vectors have unverified embedding identity; explicitly re-embed/rebuild with the selected runtime model before expecting search compatibility. Copying old vector bytes does not certify the model or dimension.

8. **Start the candidate with its own configuration.** Set both `PLATFORM_DATABASE_ENGINE=postgres` and `WORKSHOP_DATABASE_ENGINE=postgres`, all candidate database URLs, owned asset roots and the intended local model/cache. Use the candidate checkout's launcher; do not reuse the old environment implicitly. Check backend health, RAG embedding readiness, all 17 task-agent health endpoints, real login, imported owner histories, objective/solution/hint visibility and dashboard parity. Exercise one real Judge workflow, inspect its receipt/timeline and progress, and reset only a newly created verification attendee. Verify retained-evidence retry when an eligible unavailable receipt exists; do not replay a mutating tool to test it. The [browser checkpoint](judge-live-workflow-qualification.md) records representative coverage and its retry gap, not every-objective end-to-end certification.

9. **Accept or roll back deliberately.** Keep the source archive and old checkout untouched. If candidate acceptance fails, stop only the candidate's owned processes and restore access to the old stopped installation/configuration. Candidate PostgreSQL writes are not automatically replicated back to SQLite, so keep real attendee traffic off the candidate until acceptance or define a separate reconciliation plan. Never delete import markers or reset the old application to repair staging. Save per-store commit reports so recovery can identify which targets committed.

Retired alternate-server sources (`platform_secure.db`, classic SQLi/XSS and CTF-AI stores where unsupported) remain archive-only. See [remaining coverage](remaining-archive-coverage.md) for exact exclusions. This runbook does not authorize a cloud deployment or claim distributed atomicity, complete asset discovery, or lossless recovery of unexported memory state.
