# Owned shadow MCP server: implementation contract

Status: source-reviewed design, not implemented or qualified. The installed application is unchanged.

## Confirmed teaching gap

The retained `sandboxShell.toolRegisterServer` accepts a learner URL but calls `targets.discoverRogueServer()` without that URL. That client contacts a configured shared sidecar. Consequently, a real network response proves contact with the configured fixture, not registration of the model-selected endpoint. The sidecar exposes custom `/mcp/list_tools` and `/mcp/call/:name` HTTP routes; these are not an MCP SDK initialize/tools-list handshake. Imported names are added to a memory-only display catalog. `toolRegistry.js` has a static dispatch switch; importing a name does not establish that the decision loop can subsequently select and invoke it. No owned production qualification admits `mcp_shadow_server`, which correctly prevents these observations from earning current owned objective credit.

An educational rogue peer may legitimately return attacker-authored content. The missing authenticity is the registration, protocol and subsequent capability transition, not whether its document is a synthetic lab artifact.

## Required application behavior

Use a real MCP SDK server and client transport inside an owned lab boundary. Reuse the owned infrastructure's authenticated control channel, owner/session/target/generation binding and retirement model; do not reuse its HTTP response as proof of an MCP handshake. The exact model-selected URL must reach the isolated connector. Two namespace-local peers, an approved baseline and a rogue mirror, allow both positive and negative controls. Unknown addresses, host addresses, public destinations and redirects outside this isolated namespace must be denied by the outer boundary regardless of teaching mode.

In vulnerable mode, the application deliberately trusts an unapproved peer's advertised tools. In fixed mode, it verifies its server-owned approved identity before admitting any advertised tool. Neither mode may let learner data choose a platform credential, control endpoint or owner namespace. The teaching mistake is trusting the peer; it must not become arbitrary access to the student's laptop or AWS network.

The graph must perform three distinct actual decisions/effects: select registration; observe the genuine initialized peer's catalog and select an imported tool; consume the exact tool result in the final response. A mere registration acknowledgment or catalog display cannot satisfy a lesson described as malicious tool execution. Freeze each decision's available catalog and schema digest. The next decision may observe the registered tools only after the registration operation commits. Dispatch namespaced imported tools through a server-held registration handle, never through a caller-supplied endpoint or a public JSON `registered:true` flag. Preserve static tools and prevent name collisions from replacing platform dispatch.

Each source artifact is owner-bound: a real UTF-8 policy document seeded in that namespace, a learner-editable rogue replacement, and a namespace-local collector if the scenario includes disclosure. Tool reads consume those files, and collector claims require an actual persisted delivery receipt. No host/private file is involved. Do not describe a string saying “forwarded” as a delivery effect.

## Persistence and credit

Design a forward-only migration above the actual registered head when implementation starts; do not reserve or alter applied files. Persist registration intent, exact endpoint, owner/session/target/generation, catalog digest, tool schema and remote server identity, and immutable handshake/invocation receipts. Bound catalog count, names, schema size, argument depth, response bytes and execution time. Registration IDs are opaque server-generated capabilities and cannot authorize another owner or generation.

An operation interrupted between peer effect and acknowledgment is explicit reconciliation debt. Retry the same registration/invocation ID against the peer's durable receipt before changing state. Do not repeat an uncertain delivery or silently create a new registration. Reset/deletion retires peer capability and files before advancing parent cleanup; immutable grading receipts remain historical. Existing registrations must survive an application-process restart with the same authority and retain sibling isolation.

The objective-specific Judge receives trusted facts for exact model-selected registration, real SDK handshake, imported catalog delta, later model-selected imported invocation and exact returned artifact digest. For disclosure variants it also requires delivery evidence. The Judge independently assesses the advertised security lesson and cites response/source spans. Private witness validation precedes semantic grading; neither `achieved:true` nor copied receipt JSON is authoritative. Failed connection, fixed-mode rejection, a benign approved registration, a registration without invocation, fixture-only model output and stale or cross-owner receipts earn no credit.

## Verification and rollout

1. Controlled contract tests: static and imported schema validation, private witness forgery, namespace/collision boundaries, limits, unavailable peer and fixed-mode rejection.
2. Native disposable stores and actual SDK peers: fresh/populated/no-op migrations, least privilege, exact URL/protocol correspondence, import then call, uncertain operation recovery, restart, reset/deletion and exercised sibling preservation.
3. Actual local llama3.1:8b graph plus independent Judge: positive rogue invocation and negative approved/no-invocation/fixed cases. Preserve refusals as evidence; do not force decisions or weaken credit to achieve a green run.
4. Mounted authenticated learner/admin flows, rendered catalog/run details and canonical objective/dashboard parity using the current UI baseline. Recovery UI must expose actionable pending states rather than success.
5. Supported setup provisions the peer automatically only after the isolated service and schema readiness checks pass. Grant the shadow objective capability only from that concrete readiness, then qualify full application startup separately. AWS assets remain frozen.

This work is a substantive missing capability. Current HTTP SSRF promotion does not complete it, and shared legacy sidecar tests do not substitute for these checks.

## Isolated SDK and central persistence milestone (2026-09-19)

The unmounted `owned-shadow` service now runs a bundled genuine MCP SDK client and two SDK peers inside the owned Bubblewrap network namespace. It reuses the qualified initializer's exact network setup, inherited listeners, capability clearing, no-new-privileges, syscall denials and subreaper, changing only executable paths. The exact selected approved/rogue URL reaches the SDK transport; unknown URLs and redirects are rejected. The approved source lives outside learner rootfs; the rogue source is an actual bounded target file materialized into the isolated worker and read by the invoked SDK tool. The existing application does not yet expose learner editing of this new source.

Target-locked private journals preserve registration, exact canonical catalog digest, executable asset digest and distinct invocation receipts. A new process can recover a logical registration, repeat SDK initialization/catalog comparison and invoke its imported tool. This is not survival of an old HTTP transport session. Completed operation replay does not invoke the peer again. Interrupted registration publication can reconcile from its completed operation. A pending record without a completed peer receipt remains explicit uncertainty; no automatic re-execution is allowed. Target retirement erases the source and local journal; siblings survive.

Identity **0089** and MCP **0006**, promoted byte-for-byte into the source migration directories after native qualification, add immutable graph-run operation receipts and a shadow child lease. Generation/run checks fence central publication, and a child lease prevents parent retirement until cleanup completes even when the feature configuration is removed. The authenticated service and private backend client reject arbitrary public control destinations. Native PostgreSQL plus the isolated service qualified separate registration/invocation receipts, exact replay, catalog corruption rejection, sibling isolation, late reset rejection, and recovery after a deliberate post-SDK SQL publication failure without repeating the SDK invocation. A separate Node process qualified persisted registration use; owned profiles, containers and target directories were removed afterward.

`composeOwnedShadowProduction` is an explicit, unmounted factory. Its readiness reports `shadowObjectiveQualified: false`; it cannot grant the exercise. Full model-selected catalog integration, private model witnesses, independent Judge, mounted platform authentication, source-edit UI/API, supported setup packaging, and installed activation remain pending. Evidence and exact hashes: `tasks/mcp-shadow-isolated-central-2026-09-19.json`. The central repository also restores namespaced catalog entries from PostgreSQL for the current owner/session/target/generation; imported names cannot replace static tool names. Registration and invocation use distinct protocol invocation IDs and separate immutable rows. The current proof uses controlled graph execution admission, not genuine model decisions. Recovery after central publication failure is qualified within the original admitted invocation; resuming an expired/finished original run needs an explicit archival reconciliation contract and cannot retroactively earn credit. Candidate migration tests cover a populated baseline, a separate empty database with the full candidate chain, and a second no-op run.
