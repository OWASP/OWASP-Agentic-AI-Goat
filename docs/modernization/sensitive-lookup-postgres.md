# Database-backed sensitive lookup migration

The formerly MySQL-backed path and SSI API now has a native PostgreSQL implementation in the separate `sensitive_lookup` database/schema. The runtime role has SELECT privileges on teaching reference/template/config tables and INSERT/SELECT on owner-scoped exploitation logs. It has no platform access. Runtime imports never initialize databases or files; schema/seed initialization is explicit and uses a separate migration role.

Existing `/mysql/path-traversal`, `/mysql/ssi-injection`, `/mysql/combined-attack`, `/mysql/ai-chat`, `/mysql/stats` and `/mysql/health` suffixes are retained under the existing mount, including its historical duplicated `mysql` prefix. Responses identify `engine: postgres` and `dialect: PostgreSQL`. `mysqlAvailable` is false; `databaseAvailable` reports PostgreSQL health. No MySQL emulation or silent engine fallback occurs on the PostgreSQL-selected path.

The intentional interpolated reference/template SQL, arbitrary returned paths and SSI include/echo processing remain. Native examples: reference key `absent' UNION SELECT '../outside.txt' -- ` with user input `'`; template name `absent' UNION SELECT 'training template',true -- ` with user input `'`. The Boolean column requires PostgreSQL `true`, rather than a MySQL numeric convention. Raw lookups execute one extended-protocol statement in a read-only transaction. Authentication supplies log ownership; body userId never selects another learner's statistics. These auxiliary endpoints do not award canonical objectives.

Seeds are pure JSON extracted from the previous source defaults. Only synthetic DATABASE_HOST/PORT change to `postgres.training.local`/`5432`. Instructor edits survive repeat initialization. File fixtures remain a separate explicit initialization operation.

Existing MySQL data is not accessed or imported automatically. A future offline export should produce a versioned JSON document containing reference/template/config IDs and timestamps plus exploitation logs with an explicit verified owner mapping. Import must validate enums, Boolean values, required fields, unique keys and owner identities; run against an empty dedicated destination in one transaction, preserve IDs and advance sequences, and report rejected rows without silently coercing owners. Never connect runtime initialization to a MySQL server or overwrite a populated PostgreSQL destination.
