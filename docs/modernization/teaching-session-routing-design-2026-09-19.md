# Teaching sessions and composed workshop routing

Status: verified gaps; implementation and native/browser qualification pending. Preserve deliberately readable cookies, weak teaching secret and CSRF sinks. Platform bearer sessions remain canonical PostgreSQL authority. This work changes application code only.

## Evidence

`server/index.js` mounts the general `/api/workshop` router before `/api/workshop/csrf`. `server/routes/postgresWorkshop.js` applies authentication to every path entering that router, including paths it does not handle. The intended cookie-only GET/POST `/api/workshop/csrf/agent-action` therefore receives 401 before its own handler. A mounted reproduction using the actual general router, controlled authentication and a downstream sentinel returned 401 for both cookie-only methods and 200 with a valid bearer. See `tasks/csrf-umbrella-route-diagnosis-2026-09-19.json`. This does not prove browser exploitation or grading.

The current managed browser controller invokes the shared action handler through a separately owned victim surface. Existing managed-browser proofs remain valid within that scope; they do not establish that the application-mounted cookie-only URL works.

The global express-session middleware also uses the default process-local MemoryStore. Canonical JWT sessions survive process changes, but teaching cookie state does not. The CSRF router attempts to rebind a teaching cookie on a bearer request. This repairs only the process that handles that request and is insufficient across replicas. The cookie contains platform owner/session references after login; these references must be revalidated before any restored teaching state can cause an effect. Persisting arbitrary session JSON alone would preserve stale authority after revocation.

## Implementation sequence

1. Inventory each downstream router's explicit authentication requirements. Keep the existing protection of dashboard, progress, instructor, MCP and other workshop routes. Do not broadly reorder the general router and accidentally expose routes that currently depend on it.
2. Give the intended cookie-only action an explicit, narrowly matched mount with its own teaching-session authority check. Accept only a live canonical owner/session binding, including account state, expiry and revocation. An invalid presented bearer must never fall back to a cookie. Preserve the intentional lack of anti-CSRF protection in vulnerable mode; keep fixed-mode defense behavior and objective credit dependent on private browser receipts.
3. Replace supported PostgreSQL startup's MemoryStore with a bounded PostgreSQL teaching-session store. Use a forward-only migration, hashed session identifiers, expiry and deletion cleanup, minimal runtime grants, bounded JSON size, and read/write/touch/destroy methods. Avoid a new database engine or dependency when the existing pg pool suffices. Keep any explicit legacy fixture behavior isolated.
4. Prevent delayed writes from resurrecting destroyed or rotated sessions; ordinary upsert after destroy is insufficient. Model creation, rotation, update and terminal revocation explicitly. Tie teaching session lifetime to the canonical session, and integrate deletion cleanup without removing immutable evidence or sibling sessions.
5. Verify two application instances sharing the disposable PostgreSQL stores: login on one, cookie-only action on the other, restart continuity, expiration, logout/account revocation, rotation races, deletion, unavailable-store denial, and bounded cleanup. A stale cookie must not regain authority merely because a row remains.
6. Run a composed-route browser cohort for vulnerable and fixed CSRF modes, then the existing managed-browser/Judge controls. Assert no direct manual request acquires objective credit. Recheck dashboard/admin auth and teaching sinks; preserve baseline UI.

No migration number is reserved here while the current 0092/0093 work is being promoted. No installed service was restarted, no learner session was changed, and no protection was removed by this diagnosis.
