# Embedding runtime revisions

Status: **production wiring, preservation-aware migration and Transformers4.3 promotion are active locally**. This plan preserves learner documents, instructor content and historical evidence when upgrading Transformers.js from 4.2.0 to 4.3.0.

## Evidence and upgrade gate

[CPU qualification](../../tasks/embedding-transformers-430-qualification-2026-09-19.json) exercised the unchanged application `RagVectorStore` with copied, offline MiniLM assets on Node 26.9/macOS arm64. Both versions produced eight finite, normalized 384-dimensional embeddings and the same full rankings for four fictional-document queries. The candidate repeated exactly, but ONNX Runtime 1.24.3 → 1.30.0 changed components by up to 0.01545; corresponding-vector cosine similarity reached approximately 0.99509. Identical model names and dimensions therefore do not establish identical embedding semantics. This small corpus is not a benchmark-wide quality proof.

[Official registry](https://registry.npmjs.org/@huggingface/transformers/latest) and [4.3.0 release](https://github.com/huggingface/transformers.js/releases/tag/4.3.0) were checked for that qualification. The root dependency is now pinned to4.3.0 following the qualifications below; see [installed activation](../../tasks/application-embedding-activation-2026-09-19.json).

[Subsequent Linux qualification](../../tasks/embedding-transformers-430-linux-2026-09-19.json) passed on Node 26.8.2/Linux arm64 in an owned, subsequently removed container using the exact candidate lock and identical copied model assets. Eight normalized finite 384-dimensional vectors, all four expected winners and full rankings passed; repeat vectors were exact. Maximum component difference from the macOS candidate was approximately 2.98e-8. Linux amd64 and the exact Node 26.9 patch were not qualified. This satisfies the Linux arm64 CPU check only; the revision transition remains required.

Production retrieval now uses fingerprinted derived revisions with bounded rebuild admission and no original-vector fallback. Manual ingestion writes additive runtime provenance through migration0016; historical receipts remain unchanged and unattested. [Focused integration](../../tasks/embedding-retrieval-integration-2026-09-19.json), [actual CPU retrieval](../../tasks/embedding-assembled-retrieval-native-2026-09-19.json), [manual provenance](../../tasks/manual-runtime-provenance-2026-09-19.json), and [mounted student deletion](../../tasks/student-deletion-embedding-privacy-native-2026-09-19.json) passed within their recorded scopes.

The [actual persisted4.2→4.3 transition](../../tasks/embedding-persisted-42-to-43-transition-2026-09-19.json) rejects an incompatible old head, rebuilds authoritative product/manual text, preserves original receipts and sibling/historical data, and performs no new publication on repeated retrieval. It uses actual CPU runtimes in separate macOS processes with controlled lifecycle/file-receipt fixtures. Installed activation passed with exact row preservation and a complete second-initialization no-op. [Linux AMD64](../../tasks/embedding-linux-amd64-runtime-attempt-2026-09-19.json) is unqualified because the available local VM cannot execute AMD64 containers; no application code ran in that attempt.

A subsequent [exact Node26.9/Linux ARM64 qualification](../../tasks/embedding-transformers-430-linux-arm64-node269-2026-09-19.json) passed using fingerprint schema2, eight finite normalized vectors, four expected retrieval winners and identical repeated output. The owned container was removed. This closes the patch-version CPU gap, not full Linux installation or persisted-transition qualification.

Bound storage is defined by applied migrations `db/postgres/workshop-migrations/secureshop_review/0011_secureshop_bound_product_retrieval.sql` and `0012_secureshop_bound_manual_ingest.sql`:

- `product_target_retrieval_config`: `target_id`, `embedding_model`, `embedding_dimension`, lifecycle.
- `product_target_retrieval_documents`: target/generation/source-kind/source-id/chunk-index key; `body`, `embedding`, `source_sha256`. The source hash includes the vector-bearing document serialization.
- `product_target_manual_ingests`: immutable `embedding_model`, `embedding_dimension`, `document_digest`, `receipt_sha256`, extraction/file hashes and owner/session/generation bindings.
- `product_target_retrieval_ingest_receipts` and `product_target_retrieval_cleanup_receipts`: immutable operation evidence.

Existing `provision`, `replaceDocuments`, search and manual ingestion reject changed model identities. There is no non-destructive runtime-upgrade rebuild. Existing retirement deletes retrieval documents and retires the target; it is a lifecycle operation, not an upgrade mechanism. Never update applied migrations or rewrite original vector/hash/receipt rows to imply they used the newer runtime.

A standalone internal `server/services/embeddingRuntimeFingerprint.js` now snapshots the installed runtime and four fixed model assets, with five passing tests. It rejects request-supplied metadata and unavailable provenance. Loaded-session attestation now brackets offline pipeline creation with matching asset snapshots, while production retrieval integration remains pending. This module alone does not resolve mixed-runtime indexes.

## Proposed implementation

1. **Compute a server-owned fingerprint.** Introduce one shared immutable description containing model asset SHA-256 hashes, quantization, pooling, normalization, Transformers and ONNX versions, CPU backend and qualified OS/architecture. Canonically hash it. Keep the readable model identifier distinct. Resolve package versions from the actual loaded implementation, not request input. Cache only after successful pipeline initialization; changing model assets or runtime must change the fingerprint.
2. **Add derived embedding revisions.** Use the next ordered forward-only migration in `secureshop_review` (choose its number from the current head at implementation). Proposed tables: `product_target_embedding_revisions` for operation ID, target/generation, fingerprint, source-set digest, vector digest/count and publication metadata; `product_target_embedding_vectors` for revision plus original source/chunk key, original source hash and new vector; `product_target_embedding_heads` for the active revision. Retain original document rows, vectors and immutable receipts. Give runtime no direct receipt/head mutation; publish through a constrained database operation. Revoke unintended `PUBLIC` access.
3. **Re-embed authoritative text.** A bounded service reads every current owned retrieval `body`, including injected manuals and instructor-edited content. Snapshot ordered source keys/hashes and exact text into a digest. Compute candidate vectors outside the publication transaction. Do not regenerate product seeds, re-extract manuals, modify files, filter teaching payloads or manufacture replacement ingestion receipts.
4. **Publish atomically.** Lock the canonical product target, then retrieval configuration/head in a documented consistent order. Recheck active lifecycle, owner/session/launch/scenario/generation, complete source-set digest, expected prior head and runtime fingerprint. Validate vector cardinality, dimensions, finiteness and nonzero norms. Insert the complete revision/vector set and switch the head in one transaction. Changed or missing source rows reject publication. Operation replay must match all input digests; no partial active revision is visible.
5. **Use revision-aware reads and writes.** Update product retrieval metadata/search and manual ingestion to use the shared active fingerprint. A query must match that fingerprint before vector comparison. Preserve the original `embedding_model` as historical logical provenance; add explicit fingerprint/revision provenance rather than relabeling old receipts. New ingestion must atomically maintain the active derived index with its source append, or invalidate the head until a complete rebuild; it must never leave a silently incomplete searchable index. Historical receipt reads continue validating their original format. Specify the additive new-ingest fingerprint field/receipt version in the migration rather than changing old digest rules.
6. **Integrate lifecycle cleanup.** Existing authenticated reset/deletion must retire or remove derived vectors alongside their source scope and record appropriate cleanup evidence. A pending embedding computation cannot publish after reset/deletion. Preserve sibling targets and existing immutable evidence. Dependency upgrade must never invoke reset automatically.
7. **Provide a bounded operator transition.** Read-only inventory reports affected active targets and fingerprint status without document contents. Explicit reindex operates on those targets with concurrency and time limits, resumable operation IDs and digest-bound receipts. Keep unavailable/mismatch errors actionable. Do not silently use mixed versions, silently fall back to hash embeddings, or delete model caches.

Historical rows lack runtime fingerprints. Mark that provenance as unknown/legacy; do not infer a precise runtime from the old model label. Reindex their retained text into an explicitly fingerprinted revision before the new runtime serves those targets. Pending work must leave source data intact.

## Acceptance and promotion

- Fresh migration, populated upgrade and second-run no-op pass in owned disposable PostgreSQL. Runtime privileges cannot forge heads, receipts or derived revisions.
- Populate products plus multiple manuals; reindex while proving original body/vector/source-hash rows, file receipts, manual receipts, instructor content and sibling targets remain unchanged.
- Query and document fingerprints must match. Asset/runtime changes require a new revision; unchanged fingerprint/source digest is an idempotent no-op. No caller-supplied fingerprint gains authority.
- Fail embedding midway, abort the request, crash before/after publication and replay the same operation. The active revision is always complete; failure preserves the previous revision and every source document.
- Concurrent manual ingest, source replacement, reset and student deletion invalidate stale publication. Verify real lock ordering and publication races, not only mocked checks. New ingestion cannot be omitted from the active corpus.
- Real CPU qualification on Linux with supported Node and exact candidate lock: copied public model assets, offline loading, finite normalized 384-dimensional vectors, repeated output stability and representative rankings. Test platform fingerprints explicitly; do not assume macOS bitwise parity on Linux.
- Repeat changed RAG and bound product/manual workflows with actual embeddings, existing intentional poisoning behavior and owner/reset tests. Confirm historical receipts remain readable and displayed counts/content are unchanged.
- Only then update the exact root dependency pin/lock, review the lock diff for unrelated/protected changes, run relevant application tests and refresh dependency evidence. Frozen AWS assets remain out of scope; Linux CPU success alone does not qualify AWS deployment.

This design is a prerequisite for promoting the numerically changed runtime into existing bound corpora, not evidence that the broader exercise audit or deployment qualification is complete.
