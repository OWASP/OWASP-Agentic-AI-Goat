# MCP sandbox AppArmor qualification candidate

This candidate addresses the measured Ubuntu user-namespace restriction in the
local Colima profile without changing global sysctls or granting Docker
capabilities. Grant 08 remains a failed qualification: the kernel transitioned
`bwrap` from `unconfined` to `unprivileged_userns`, then denied `setpcap` and
`net_admin`; bubblewrap could not assign `127.0.0.1/8` to its private loopback.

The policy template is derived from Moby's Apache-2.0 default container profile
at commit `61eaf32614c7c71b60bd8927d3e6a4ffc8ff1f31`. The supervisor retains its
network, proc/sys, signal and mount restrictions and has no `userns` rule. It
uses AppArmor ABI 4.0 so absence of that rule is enforceable rather than hidden
by an older policy ABI. Only executing the packaged `/usr/bin/bwrap` performs a
named transition to the local `bwrap` profile. That child allows the namespace,
mount and setup capabilities required by bubblewrap 0.12.0. The existing
`--unshare-user --unshare-net` invocation, a root-owned final-process seccomp
filter, tmpfs root and exact
target binds remain unchanged. The rules permit capability checks; they do not
add capabilities to the outer container or retain setup capabilities in the
learner process.

This source is not installed or selected by Compose. A future one-use native
qualification must:

1. Read the exact Docker grant and query its exact daemon. Capture the named
   VM's kernel, AppArmor feature/sysctl state, active Docker security options,
   `dpkg-query` bubblewrap version and pre-run audit cursor.
2. Render a unique twelve-hex-suffix profile and write it to an owned temporary
   path. Require that exact profile name to be absent first, exclusively create
   an owned mode-0700 VM directory, and copy the mode-0600 policy there through
   Lima's generated SSH configuration.
3. Run `apparmor_parser --skip-kernel-load` first. Load only that unique profile,
   verify it is present, and start the owned runner with
   `apparmor=<unique-name>` and the existing seccomp setting.
4. From the Node supervisor profile, run a direct `unshare --user --map-root-user
   /bin/true` negative and require one kernel-audit record to contain DENIED,
   `userns_create`, the exact unique profile and `comm="unshare"`; matching
   fragments from different records are insufficient. This must not use bwrap.
5. Through production `executeTarget`, require bubblewrap success, absent host
   root/sibling/journal/pristine paths, no external network, exact target writes,
   and the existing held-process-versus-retirement serialization and receipt.
   The final sandbox deliberately exposes an empty `/proc`: current MCP
   exercises use Bash, Node, coreutils and curl but do not require procfs.
   Require those runtimes to work, prove an outer-container sentinel PID is not
   signal-visible, and prove an outer-container HTTP listener is unreachable.
   Procfs-dependent learner commands such as `ps` are unsupported by this owned
   exercise runner. Capture `/proc/<outer-bwrap-pid>/attr/current` from the
   supervisor's container namespace as the same uid during setup to prove the
   intended parent-to-child transition without exposing procfs inside the
   sandbox. The profile grants only parent `ptrace read` and child `readby` for
   that relationship; it does not grant cross-profile trace or mutation.
6. Start a second owned runner under the same profile with a real long-running
   `executeTarget` child. After its readiness marker and child label are read,
   stop the container with a bounded deadline and require the child and
   container to terminate. This proves runtime stop/force-removal signals reach
   the child even when the supervisor cannot coordinate a normal return.
7. In an unconditional cleanup block, remove every owned container and image,
   query whether a profile appeared after every attempted load (including a
   timeout), unload only that proven-owned exact unique profile with
   `apparmor_parser -R`, then prove exact kernel-profile absence before deleting
   its policy, marker and exclusive directory. A failed unload or uncertain
   profile query retains those recovery inputs and records cleanup debt. Query
   Docker, AppArmor and the remote path for exact absence. A load, test, unload,
   deletion or absence-query failure makes the qualification terminal-fail.

## Local installation design

After the unique-profile gate passes, the supported local installer may render
the stable name `owasp-ai-goat-mcp-sandbox` into a private temporary file. It must run
the AppArmor parser's no-load validation first, compare the generated bytes with
any installed application-owned policy, then copy the candidate atomically as a
root-owned `0644` file under `/etc/apparmor.d/`. Loading or replacing the stable
profile occurs only after the file is durable. Compose can then select
`apparmor=owasp-ai-goat-mcp-sandbox`; it must stop using `apparmor=unconfined` in the
same reviewed activation change.

An upgrade retains the prior policy bytes until the replacement parses, loads
and passes a supervisor-negative/bubblewrap-positive smoke check. Failure
restores and reloads those exact prior bytes. Uninstall first stops the runner,
unloads only `owasp-ai-goat-mcp-sandbox`, removes only its application-owned policy and
verifies exact profile and file absence. The installer never edits Ubuntu's
AppArmor package profiles, parser configuration, user-namespace sysctls, Docker
daemon configuration or another application's policy. Installers that cannot
load and select this profile must leave strict MCP effects disabled.

The qualifier must not change AppArmor sysctls, Docker capabilities, privileged
mode, host networking, host-root mounts or AWS files. Until the same policy and
tests pass on the supported local installer profiles, strict MCP runner effects
remain unavailable for grading.

## Grant 09 procfs finding

Grant 09 passed the direct-supervisor AppArmor denial and entered the named
`bwrap` child profile, then Bubblewrap 0.12.0 failed its `--proc /proc` mount
with `EPERM`. The exact kernel journal contains no corresponding AppArmor mount
denial. That absence alone does not prove which kernel check returned the
error. It is, however, consistent with Linux's user-namespace procfs visibility
rule: the exact Docker daemon masks multiple non-empty paths below the parent
container's `/proc`, and Linux rejects a new procfs mount from a user namespace
when an existing procfs instance is not fully visible. Bubblewrap's
`SETUP_MOUNT_PROC` calls `mount("proc", ..., "proc", MS_NOSUID | MS_NOEXEC |
MS_NODEV, NULL)` and cannot request the kernel's `subset=pid` exception.

The candidate therefore creates an empty `/proc` directory instead of mounting
procfs. It retains the private user, mount, network, PID, UTS and IPC namespaces,
the minimal tmpfs root, and exact target binds. This removes information rather
than exposing an outer procfs or host root. A native requalification is still
required for the behavioral assertions above; argument inspection is not proof
that the namespaces isolate a running learner command.

Grant 10 tested that candidate once and failed before the final root was
entered. Bubblewrap implements `--disable-userns` by opening the original
`/proc/sys/user/max_user_namespaces` with `O_WRONLY`. The matching kernel audit
record shows the exact `bwrap` child profile denied `CAP_SYS_RESOURCE`, which
Linux requires to write that user-namespace limit. Docker also locks `/proc/sys`
read-only, so adding the AppArmor capability alone is not a complete fix. Grant
10 remains a terminal failure with exact cleanup; it does not qualify the empty
proc contract. A subsequent candidate must preserve the prohibition on nested
learner user namespaces without exposing or making the parent's proc sysctls
writable.

## Final-process seccomp candidate

The next candidate removes `--disable-userns` and gives Bubblewrap a compiled
classic-BPF filter through `--seccomp 3`. Bubblewrap installs that filter after
namespace and mount setup and before it executes the learner command. The
filter follows Flatpak's LGPL-2.1-or-later sandbox policy pattern: `clone3`
returns `ENOSYS` so libc falls back to `clone`, `clone(CLONE_NEWUSER)`,
`unshare`, `setns`, the legacy mount calls, `pivot_root`, and `chroot` return
`EPERM`, and the newer mount API returns `ENOSYS`. Ordinary `clone` remains
available, so Node worker threads and child processes are expected to work.
The generator accepts only the native `amd64` or `arm64` architecture.

The image builds the policy with libseccomp and installs the BPF plus canonical
architecture/SHA-256 metadata as root-owned non-writable files. The runner
opens each with `O_NOFOLLOW`, requires the configured trusted uid (root in the
shipping image) and no owner/group/other write bits, then checks type, size, architecture and
digest, then passes the same already-verified BPF descriptor as fd 3. It never
reopens the policy by pathname. The descriptor is closed by the supervisor on
both successful spawn and synchronous spawn failure. Missing, malformed,
oversized, writable, symlinked, wrong-architecture or changed policy material
fails closed; there is no unfiltered execution path in `executeTarget`.

The native gate must invoke every learner command through `executeTarget`.
Besides the existing filesystem, PID, network, restart and retirement checks,
it must run the packaged raw-syscall probe and require the exact errno contract,
then prove a Node worker and a normal child process still complete. This is
source and pure-test evidence only until a new single-use native grant tests the
compiled filter under the reviewed Linux profile.

Grant 11 built all three images and passed the first real filtered target
command, then failed because the clean sandbox `PATH` omitted
`/usr/local/bin`, where the official Node image installs Node. `/usr` was
already mounted read-only, so this was path discovery rather than a missing
filesystem bind. The corrected candidate keeps that existing `/usr` mount,
adds `/usr/local/bin` to the fixed clean `PATH`, makes the exact regular
`/usr/local/bin/node` file mode `0555` during the image build, and verifies it
and the packaged syscall probe are canonical-path, root-owned, non-writable
executables before constructing an invocation. It does not add another
`/usr/local` or host-root bind. Grant 11 remains terminal-fail; its later
syscall, process, isolation, retirement and stop assertions did not run.

Libseccomp can resolve a known syscall that does not exist on the native ABI to
a negative pseudo-syscall number. The generator resolves each name explicitly
for the one native architecture: it skips only those known negative pseudo
numbers because no native syscall can reach them, rejects an unknown name, and
uses exact rules for real syscall numbers. `clone` is mandatory on both
supported architectures and its absence fails the build rather than weakening
the nested-user-namespace rule.

Grant 13 qualified the corrected candidate on the owned aarch64 Linux profile.
The actual compiled filter returned the required errno values for raw nested
namespace and mount syscalls while Node workers and child processes succeeded.
The same production execution path passed target mutation, host-root and
sibling exclusion, empty-proc, PID and network isolation, restart recovery,
execution-versus-retirement serialization, immutable receipt replay and stale
capability fencing. A separate long-running Bubblewrap process received the
expected child AppArmor label and terminated under bounded container stop.
Every owned container and image was absent afterward; the unique profile was
unloaded and absent, its remote policy directory was absent, and no cleanup
debt remained. This qualifies the reviewed local profile only; AWS and other
installer/kernel profiles remain outside this evidence.
