# Student deletion: required implementation

Status: design accepted within the authorized architecture repair scope; implementation and qualification remain open. This does not declare the current delete endpoint functional.

## Observed failure

`server/routes/postgresAdmin.js` exposes level-2-only DELETE `/students/:studentId`, rejects self-deletion, and invokes `adminRepository.deleteUser`. The repository now constrains its mutation to student/admin_level=0 in the statement itself. The identity runtime role lacks DELETE on identity.users. Even with that grant, restrictive references from objective_judgments, objective_evidence and activity_logs prevent deleting an active learner with evidence. Separate workshop databases cannot participate in identity foreign-key cascades. The current UI promises account, progress and all associated data removal, which the implementation cannot deliver.

## Decision

Implement durable deletion with a retryable job and explicit terminal acknowledgement. Do not replace deletion with an account deactivation silently. Do not grant table-wide DELETE as a standalone repair. Preserve the current modal and dashboard layout; use existing loading/error feedback for the job state and revise text to describe any deliberately retained, non-content audit tombstone accurately.

1. Admission: authenticate current platform session, require level 2, validate target integer, reject self and non-students. Lock the target user, atomically mark inactive and insert a unique deletion job. Record requesting admin, target internal ID, requested time, state and per-store cleanup status. Repeated requests resolve the same job. Existing user-end triggers revoke SecureShop launches; explicitly revoke remaining sessions and invalidate graph owners so pending actor/Judge writes cannot recreate data.
2. Cleanup registry: enumerate every student-owned store from the exercise inventory. Each adapter accepts only the server-selected internal owner ID and deletes that owner's progress, evidence, conversations, artifacts and synthetic lab state. Each operation must be idempotent and return a bounded receipt. Never delete shared Mailpit mail, whole challenge tables, unrelated files or another learner's rows. Immutable import provenance is historical control data: retain its non-content mapping/digest tombstone and document that exception rather than modifying immutable source records.
3. Graph coordination: invalidate every registered family for the owner and wait for/resolve admitted effects before deletion. Retain a non-content deletion barrier until all cross-process writes are fenced. Cleanup may fail or outlive an HTTP connection; neither permits reactivation or false success.
4. Identity cleanup: remove raw objective evidence, judgment response content, recovery packets and conversation payloads. Preserve only the explicitly defined minimal administrative deletion receipt. Resolve existing restrictive references using reviewed forward migrations or transaction-scoped deletes; never disable FK enforcement or rewrite applied migrations. Role-scoped SQL must prevent deleting administrators even if their role changes during admission.
5. Finalization: after all required store receipts are complete, remove the student identity and release its username/email. Keep the deletion job's opaque target identifier and completion receipt independent of the deleted FK. Return completed only now. A failed cleanup leaves access revoked and the job retryable with a stable error category; the administrator sees pending/failed rather than a success toast.
6. Integration: use the same registry for local and AWS application execution. No CloudFormation, image, deployment script or cloud resource changes are in scope. Do not activate a job/migration before fresh-install, upgrade and recovery qualification.

## Required verification

- Real PostgreSQL with actual authenticated admin and student sessions: student denied, level-1 admin denied, level-2 allowed, self/admin target denied, invalid IDs rejected before mutation.
- Populate a student with a real accepted Judge receipt, evidence, progress, conversation and active SecureShop launch; complete deletion and prove all required owned content is removed while another student's content is byte-for-byte preserved.
- Race deletion against chat, objective completion, reset and role promotion. No post-deletion credit, restored session or new artifact may appear.
- Inject failure in each cleanup adapter and a process restart after each committed phase. Repeated requests resume without repeating unsafe effects or claiming completion early.
- Verify actual Mailpit/file cleanup only on owned fixtures. In-memory receipt loss is not durable cleanup proof.
- Fresh and upgraded migrations retain checksums and least-privilege runtime behavior. Browser modal/dashboard reports pending/failure/completion accurately without layout changes.

Next implementation step: inventory adapter owner keys and durable write fences, then draft the identity deletion-job schema outside startup discovery and implement its admission/recovery repository. Existing `mcpConversations.integration.test.js` intentionally still exposes the unresolved runtime deletion failure; do not weaken that assertion to a migration-role delete.

## Journal draft and repository contract

`drafts/student-deletion-journal.sql` now defines one retained job per internal student ID and ordered cleanup steps. It stores no email, prompt, file contents, raw provider errors or learner credentials. A running job requires a lease token and expiry; terminal timestamps agree with terminal state. A worker may claim only pending/failed jobs or expired running leases. Every acknowledgement must match the current unexpired token, so an old worker cannot finish work after another worker takes over.

The repository must admit the job in the same transaction that locks and deactivates the target, checks current requesting-admin authority, and revokes sessions. Its step manifest must come from the application cleanup registry, never the request body. Job completion must lock the job and verify every required step is completed; SQL grants alone do not enforce that rule. The draft intentionally is not ready for activation until admission, leases, completion invariants and authenticated HTTP behavior are implemented and proven on PostgreSQL. Lease expiry does not undo an external effect; adapters still require idempotency or an uncertain-result reconciliation path.

Recovery discovery now reads pending jobs, expired running leases and failed jobs older than a bounded retry delay. It returns at most 100 opaque job IDs (20 by default), ordered by last update and ID; it does not return account or effect content. Discovery grants no authority: each worker must still win the atomic claim. A fresh repository instance on native PostgreSQL verifies pending discovery, live-lease exclusion, expired-lease recovery and delayed failed-job discovery. The composed identity/Excessive Agency cleanup regression also passes. No background scheduler, HTTP activation or complete cleanup registry is enabled by this change.

## Independent review: activation gates

- The future-run insertion barrier does not drain pre-admission runs. Require a first cleanup step that invalidates and drains every owner family before data destruction. The shared family registry now includes the previously omitted `SensitiveLookup`; actual HTTP inspector tests prove its owner-scoped visibility, but connected deletion blocking for that family must also pass native qualification.
- Recheck lease authority in the final state mutation of acknowledgement, failure and completion transactions; a lease valid before a blocked SQL statement may have expired by its completion. Native lock-delay tests must prove rollback rather than expired-worker acknowledgement.
- Require terminal identity cleanup and verify the user is absent before acknowledging it. A false adapter receipt must leave a retryable identity step, not a permanently completed step that prevents finalization forever.
- Before scheduling, add bounded renewal/cancellation and shutdown draining. An expired lease cannot undo an external effect; adapters need idempotency and uncertain-result reconciliation.
- Manifest mismatch needs a job-level durable failure/backoff or quarantine. Repeated expired-lease recovery with a mismatched manifest must not become a hot loop.

These are application activation requirements, not changes to AWS deployment assets.

Manifest mismatch now has durable quarantine rather than automatic retry: the worker stops before further adapter dispatch, the repository independently confirms the mismatch under the current lease, and the job retains its steps, receipts and run blocks. Quarantined jobs cannot be claimed or age into recovery discovery. Resumption requires a currently active level-2 administrator and a server manifest exactly matching the recorded ordered steps; it restores only pending job state, never account access or completed cleanup steps. No public quarantine/resume API is activated yet.

Fresh PostgreSQL18 qualification proves completed-prefix preservation, zero adapter calls under a changed manifest, exclusion from recovery after a year-old timestamp, rejection of stale lease/matching-manifest quarantine, denied student/level-1/inactive-admin resumption, exact-manifest privileged resumption and one winner for concurrent resume requests. Original deletion and run-drain regressions pass in separate owned databases. Evidence: `/tmp/dvaia-deletion-quarantine-proof-LCUYhM/{quarantine,original,drain}.log`. The tested repository, worker and draft schema match the source at this checkpoint; the owned container was removed. The identity-delete fixture remains migration-role-only and is not production cleanup coverage.

The internal worker now accepts a real AbortSignal and bounded lease duration, renews at one third of that duration, and supplies explicit jobId, signal and lease-check capability to adapters. On cancellation it waits for the adapter and any in-flight renewal to settle, and does not start acknowledgement or failure recording afterward. It cannot forcibly cancel an arbitrary adapter or undo an already-started external effect; adapters must honor the signal/check and reconcile uncertain outcomes. Scheduling and process-wide shutdown orchestration remain unmounted.

The partial registry now includes `revoke_runs`. Its drain confirms the complete committed block set for the job/owner, bumps every registered generation before waiting, and acquires/releases advisory locks serially in deterministic code-point order. Ledger acquisition receives a bounded abort signal rather than racing an uncancelled promise. PostgreSQL queries retain the existing pool and statement timeouts; cancellation is checked around those queries and is not a claim of instantaneous SQL cancellation. Twenty-two focused worker, admission, adapter and coordinator checks pass; native composition is recorded separately after qualification.

Repository manifests must now begin with `revoke_runs` and end with `identity`; a cleanup plan omitting either boundary is rejected before admission. The actual partial adapter registry is exercised by the composed native test, rather than substituting a successful reset response for cross-family draining. This enforces ordering of registered phases, not completeness of the remaining store inventory.
