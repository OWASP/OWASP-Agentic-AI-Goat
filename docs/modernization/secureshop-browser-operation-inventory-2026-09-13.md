# SecureShop browser operation inventory

**Status:** read-only source inventory for a future opaque-origin iframe bridge. The current CORS and iframe checks prove only browser primitives; no live bridge, platform-owner binding, or connected qualification exists.

## Current browser contract

SecureShop is routed inside the main React application at both `/secureshop/*` and the transitional `/secureshop/v2/*` alias (`client/src/App.js:635-734`). Public landing, login, registration, catalog, product, and cart routes coexist with authenticated customer, merchant, and admin routes. `RequireAuth` redirects within those paths and preserves the requested pathname/query (`client/src/pages/secureshop/components/RequireAuth.jsx:18-43`). A frame must preserve React navigation, query strings, hashes, back/forward, refresh/deep links, role redirects, and both aliases even if the parent address bar does not mirror every inner navigation.

All application data calls use `fetch`; there is no native `EventSource`, WebSocket, XHR, or Axios use inside this subtree. `AuthProvider` globally replaces `window.fetch` so same-origin `/api/secureshop/*` calls receive the SecureShop bearer from localStorage, while an explicitly supplied Authorization header wins (`client/src/pages/secureshop/context/AuthContext.jsx:55-84`; `client/src/utils/secureShopFetch.mjs:1-26`). This global patch is incompatible with a safe parent bridge: the replacement must classify a closed set of operations and must never forward an arbitrary URL, method, headers, or platform credential.

The typed bridge should expose names such as `catalog.list`, `cart.add`, `agent.chat`, and `admin.policy.render`, with an exact method/path template and schema for each. The trusted parent supplies only the current shop bearer and future immutable launch context. It must reject path fragments, extra headers, absolute URLs, unknown query keys, body owner overrides, platform prefixes, and an operation/role combination outside the current contract. Existing shop `user_id`, `author_id`, inbox owner, retailer, URL, template, command, and role fields remain available to the vulnerable application where the lesson depends on them; they must never become platform-owner authority.

## Streaming

Agent chat is a POST carrying JSON and `Accept: text/event-stream`, then manually reads `Response.body` with `ReadableStream.getReader()` and parses `event:`/`data:` frames. Events are `tool_call`, `tool_result`, `assistant_message`, `done`, and `error`; component unmount cancels the reader (`client/src/pages/secureshop/hooks/useAgentStream.js:41-99,102-131`). The direct Orders refund call does not parse the stream and only waits for fetch completion (`client/src/pages/secureshop/pages/Orders.jsx:65-76`).

Use a typed `agent.chat.start` request returning a bridge request ID, followed by ordered `agent.chat.event` messages carrying the existing event name and payload unchanged. Add `agent.chat.cancel(requestId)` and propagate cancellation to the backend fetch/reader. Authenticate every message with the frame channel nonce and `event.source`; enforce one terminal event, per-stream sequence numbers, bounded pending streams, and cleanup on navigation. Do not collapse the stream into a fabricated JSON answer or use the final assistant text as proof of tool effects.

## Files, media, downloads, and external resources

- Upload uses drag/drop or a file input, constructs a new `File` with the learner-editable filename, and sends multipart fields `file`, `kind`, `scope_id`, `mime`, and `public` (`client/src/pages/secureshop/components/UploadZone.jsx:16-58,75-106`). A typed upload bridge must structured-clone the `File`/`Blob` plus these exact fields, preserve the crafted filename and content, and return the current JSON result. It must apply only transport/resource bounds already compatible with the exercise; normalizing the filename, MIME, SVG, polyglot bytes, or path would invalidate the upload and traversal lessons.
- The current frontend does not call `/uploads/download`. Admin audit export is generated entirely in the browser with `Blob`, `URL.createObjectURL`, a temporary `<a download>`, and revocation (`client/src/pages/secureshop/pages/admin/Audit.jsx:103-119`). The iframe therefore needs `allow-downloads` and a browser test for the CSV filename/content. It does not need a generic server-download bridge at this checkpoint.
- Product/listing images load from `/api/secureshop/uploads/static/...` or arbitrary `http(s)` URLs; fallback product art and fonts also use external origins (`client/src/pages/secureshop/utils/assetUrl.mjs:1-8`; `Product.jsx:94-103,176-218`; `ProductCard.jsx:24-53`; `pages/merchant/Listings.jsx:247-255`; `theme.css:4`). These are element/CSS fetches, not calls visible to a fetch shim. Qualify them in the actual opaque frame. If mediation is needed, use a narrowly typed asset operation or reviewed CSP/proxy mapping; never turn the parent into an arbitrary URL fetcher. Preserve the server-side SSRF exercises, whose learner URL is sent as JSON/query to a SecureShop endpoint and fetched by the challenge backend.
- Merchant Inbox invokes `window.print()` (`client/src/pages/secureshop/pages/merchant/Inbox.jsx:272-286`). Dialogs and toasts use portals into `document.body`, and multiple pages install document-level keyboard/pointer handlers (`client/src/pages/secureshop/components/Dialog.jsx:21-58,108-116`; `ToastContext.jsx:67-77`). Those should continue inside the frame without bridge authority, but printing, focus restoration, scroll locking, and escape-key dismissal need browser checks.
- The footer has an external `_blank` GitHub link (`client/src/pages/secureshop/components/Footer.jsx:44-53`). A sandbox without popup permission blocks it. If popups are retained, use the smallest sandbox permission and `noopener`; do not grant top navigation or let a challenge popup escape the sandbox implicitly.

## Storage and authentication adaptation

An opaque sandbox cannot rely on the current origin's Web Storage. SecureShop reads/writes `secureshop_v2_token` and `ss_guest_cart` (`client/src/pages/secureshop/context/AuthContext.jsx:15-23,86-92`; `CartContext.jsx:26-37,54-79,116-129`), while Account independently reads the token (`client/src/pages/secureshop/pages/Account.jsx:22-27`). Storage failure is caught, but it degrades into lost authentication after reload, undecorated API calls, and a guest cart that cannot persist.

Provide a namespaced SecureShop-only storage adapter with exactly those two keys, or move the shop token into channel state and expose typed shop login/logout/current-user operations. Inner SecureShop XSS must retain access to vulnerable **shop** state if token theft is part of the lesson. It must never read the platform token, launch cookie/capability, parent storage, arbitrary storage keys, or raw bridge authorization. The parent should bind persistence to the verified platform launch and frame channel; clearing shop auth must not revoke the platform launch, and platform logout/revocation must terminate the channel and erase its shop state.

## Exercise-preservation risks

| Risk from bridge/iframe adaptation | Required preservation check |
| --- | --- |
| Sanitizing HTML or executing it in the parent would change the XSS boundary. Raw review, listing, email, config, agent reply, and hop preview HTML currently executes through `dangerouslySetInnerHTML` inside SecureShop (`client/src/pages/secureshop/components/ReviewCard.jsx:45-54`; `AgentLane/Turn.jsx:40-51`; `AgentLane/HopDetailSheet.jsx:88-107`; `pages/merchant/Inbox.jsx:278-288`; `pages/admin/System.jsx:218-235`). | Keep raw HTML rendering inside the opaque frame. Prove script can affect the inner shop DOM/shop state but cannot read parent DOM/storage/cookies, invoke a platform bridge operation, or select another learner owner. |
| Rewriting learner fields can erase authentic IDOR, injection, SSRF, SSTI, XXE, upload, policy-poisoning, MCP-registration, and excessive-agency mechanisms. | Typed validation checks shape and resource bounds, while preserving the exact vulnerable shop identifiers and payload strings passed to the named SecureShop operation. Immutable platform ownership is injected out of band and cannot be supplied by those fields. |
| A generic parent fetch or asset proxy would let inner XSS request `/api/auth`, `/api/admin`, launch/reset/Judge APIs, or arbitrary network targets with parent credentials. | Closed operation registry only; no URL operation, no arbitrary headers, no ambient parent cookies/token forwarding, and platform CORS/null-Origin rejection remains defense in depth. |
| Hiding all shop tokens would remove auth/JWT lessons; exposing a launch capability would destroy ownership isolation. | Keep the intentionally vulnerable shop identity available within the frame and test its attacks within one scenario. Keep the platform owner/launch capability entirely parent/server-side. |
| Buffering, reordering, or synthesizing agent events can make the model/tool observation story fictional. | Preserve ordered event payloads, cancellation, errors, terminal reason, and trace IDs. Grade only server receipts/observed effects bound to the immutable launch. |
| Broad CSP or blocked external subresources can silently change product rendering and payload reachability. | Qualify uploads/static assets, external images/fonts, inline SVG, stored SVG behavior, and each XSS fixture in the actual sandbox policy. Do not count a payload string as execution proof. |
| BrowserRouter, reload, popup, print, blob download, portals, and focus behavior may differ in a sandbox. | Run deep-link/refresh/back-forward tests for both route aliases plus focused print/download/modal/navigation checks. Keep visual UI and learner wording unchanged unless a curriculum update explicitly explains a real semantic change. |

## Minimum bridge qualification

Before calling the iframe integration complete, run a browser matrix that exercises one representative operation for every row above; all four mutation verbs; login, reload, logout, and role change; simultaneous JSON calls; a full multi-hop streamed agent turn plus cancellation/error; multipart upload with crafted filename and bytes; uploaded/static and external image rendering; local CSV download; deep links and history; and XSS attempts against parent storage and platform APIs. Add per-operation negative tests for unknown paths, methods, headers, query/body keys, response types, stale nonce, wrong `event.source`, replay, oversized messages, and channel teardown.

That qualification must also prove that two platform learners using the same vulnerable shop persona cannot exchange storage, streams, API responses, effect receipts, trace/Judge data, or reset state. The current frontend inventory supplies the operation surface only; it does not establish that ownership boundary.
