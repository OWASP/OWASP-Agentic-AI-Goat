# CSRF exercise authenticity review

Decision: **revise**, preserving the existing interface and intentional vulnerable action. The learning objective is valid, but current execution and grading do not establish the browser boundary they advertise.

## Findings and executed evidence

- `CSRFWorkshop.js` uses same-origin `srcDoc` and Blob execution. A successful preview therefore does not establish a cross-origin attack.
- `csrfWorkshop.js` infers `direct_post`, `direct_get` and `fetch` from HTTP shape. `csrfObjectiveGrader.js` combines these labels with a real victim-state effect. Direct HTTP clients can reproduce these inputs without browser provenance.
- The real session cookie explicitly uses `SameSite=Lax`. A different port on the same hostname provides a same-site, cross-origin teaching boundary. Cross-site POSTs withhold that cookie; `credentials:include` does not override this policy.
- Actual `applicationCors.js` reflects challenge origins with credentials enabled. JSON preflights succeed and responses are readable. Both `csrf_p2` templates now describe this behavior accurately; their executable payloads are unchanged.
- The defense's sandbox `sameSite:Strict` metadata does not change the real cookie. Even a real Strict cookie does not prevent a same-site, cross-origin request. A synchronizer token or explicit origin validation must establish the defense outcome.

`node --test tests/csrfBrowserOriginBoundary.test.js` passes one real Chrome/152.0.7977.75 test. Owned loopback servers, synthetic sessions and a fresh browser demonstrate same-origin and same-site form authentication, absent cross-site authentication, successful JSON preflights, and readable responses using the actual CORS middleware. Only owned fixture state is mutated; browser and listeners are closed. This does **not** execute the production actor, database, agent or Judge.

Browser semantics agree with primary references: [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [MDN CSRF](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF), and [MDN Sec-Fetch-Site](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site). Request headers are useful diagnostics, not sufficient proof against a non-browser client that can forge them.

## Implementation contract

1. Admit a bounded, one-use attempt under the authenticated owner's existing run/generation. Persist the exact raw HTML digest, objective, mode and explicitly configured attacker/victim origins. Never derive trusted origins from query parameters, Host or forwarded headers.
2. Execute the learner's raw HTML in an application-owned ephemeral browser context. Supply only an opaque challenge victim session; never copy platform cookies, JWTs or localStorage. The browser service needs restricted network destinations, concurrency/queue limits, deadlines and cancellation cleanup.
3. Observe navigation/frame initiator, actual request, eligible cookie presence, response and before/after victim state outside learner JavaScript. Keep private attempt correlation out of learner pages and Judge DTOs. Integrate with the actual victim action without executing the payload twice.
4. Require a server-owned receipt matching owner, generation, run, objective and payload digest before Judge credit. A state delta is required for exploitation; an observed attempted request, actual rejection and unchanged state are required for defense. Direct calls, copied headers, postMessage and supplied receipts cannot qualify.
5. Fence reset, expiry and replay; close browser contexts and reject stale completion. Fixed mode must enforce a real synchronizer token and/or explicit origin policy. Preserve the intentional global Lax setting and vulnerable-mode sink.
6. Connect Execute to observed execution while retaining the baseline controls and SSE workflow. Copy, download and manual new-tab execution remain practice paths unless independently observed. Explain this distinction accurately in the existing interface.

## Acceptance gates still open

Connected tests must prove vulnerable success, fixed rejection, unchanged raw payload, negative controls, owner isolation, duplicate rejection, reset during execution, stale Judge rejection and resource cleanup. Test administrative objective visibility and dashboard parity after integration. Local same-site origins and configured hosted origins require separate connected qualification. No AWS or deployment change is included in this application design.

The exercise remains unqualified until these gates pass. This review and the browser-policy test do not close the broader authenticity goal.

## Connected integration seams

The implementation should add one authenticated launch operation, `POST /api/workshop/csrf/browser-attempt`, with a route-local JSON size limit and the request body `{ tab, objectiveId, html }`. The server must validate that the objective is currently visible, belongs to the selected GET or POST tab, and uses the Payload Builder. The raw `html` bytes are the learner artifact; retain them unchanged for execution and bind their SHA-256 digest into the attempt. The configured attacker and victim origins are server configuration, never request fields.

This launch route is the single owner-coordinated operation. Wrap it in the existing `ownerWorkflowRoute(ownerRuns, req => getUserKey(req), ...)` seam in `server/routes/csrfWorkshop.js`. That wrapper captures the execution and creates the Judge attempt before handler work at lines 199-215. `server/agent-runtime/runCoordinator.js` serializes an owner's runs through `owner.tail` and, in PostgreSQL mode, `server/agent-runtime/postgresRunLedger.js` holds an advisory lock for the complete run. If the managed browser calls the currently wrapped `/agent-action` route, the nested run waits for the launch run to finish while the launch run waits for the browser response. That is a deadlock.

Avoid that deadlock with a private active-attempt registry and direct execution-context re-entry:

1. The outer launch handler registers the captured execution, its `csrfGrading` context, owner ID/key, run ID, local and durable generations, tab, objective, payload digest, deadline and cancellation signal.
2. The application-owned browser receives an unpredictable, HttpOnly, host-only challenge victim cookie with `SameSite=Lax`. It must not receive the learner's platform `connect.sid`, JWT or local storage. The cookie maps only to the active synthetic VaultLink victim and expires with the attempt.
3. Immediately before allowing the forged request to continue, browser request interception records its frame, initiator, URL, method and resource type in the private attempt. `Origin`, `Referer` and `Sec-Fetch-*` may be retained as explanatory observations, but they are not authority.
4. A small `/agent-action` dispatcher resolves the managed challenge cookie before the normal `requireWorkshopUser` branch. For a valid active attempt, it consumes the allowed request and calls `withOwnerExecution(attempt.execution, () => handleAgentAction(req, res))` directly. It must not call `ownerWorkflowRoute` or begin another Judge attempt. Existing manual requests continue through `requireWorkshopUser` and the current owner-coordinated route, preserving the intentional sink and practice behavior.
5. The direct path checks the captured execution before action execution, before receipt and grading, and after response publication. The outer handler revokes the registry entry and closes the browser context in `finally`, including timeout, client cancellation and reset.

The managed challenge cookie and private registry entry must agree on owner, run, generation, tab and one-use request allowance. A learner cannot obtain the cookie because arbitrary HTML runs only inside the managed context. A copied `Origin`, `Sec-Fetch-Site` header, request body or public response remains insufficient. The route may continue accepting those direct requests as an intentional vulnerable practice sink, but they must not complete the browser objectives.

`handleAgentAction` in `server/routes/csrfWorkshop.js` is the correct common effect seam. Capture the relevant victim state before the action. For managed requests, combine the private browser observation with the actual server result and state after the action, then call `noteGradeReceipt` before either `creditObjective` loop. The blocked loop is around lines 397-413 and the successful loop is around lines 423-444 in the current source. The receipt for an exploit requires the exact payload digest, one browser-observed request and a concrete state delta. A defense receipt requires that observed request, the actual HTTP 403 now produced by `server/services/csrfForgedResponse.js`, and unchanged state. The grader in `server/services/csrfObjectiveGrader.js` must require this receipt for `csrf_g2`, `csrf_g3`, `csrf_p1`, `csrf_p2` and `csrf_p3` and advance the rubric version. Receipt evidence sent to the Judge must omit the cookie, registry key and other bearer material.

The current reset wiring already supplies the necessary ownership fence. `runCoordinator.reset` increments the local generation, aborts active runs and waits for their queue entry before cleanup. The PostgreSQL ledger advances the durable generation before waiting for its advisory lease. Both tab and full reset routes in `server/routes/csrfWorkshop.js`, and the global adapter in `server/services/postgresWorkshopResetService.js`, use this coordinator. The browser observer must subscribe to the captured abort signal so reset immediately revokes the attempt and closes its page/context. Cleanup then runs after the outer attempt drains. A tab reset therefore cancels the current owner run before clearing only that tab; it must not attempt a second nested owner reset from the browser service.

## Frontend request contract

`client/src/pages/challenges/CSRFWorkshop.js` currently keeps the edited artifact in `payloadHtml[tab]`. `executePayload` only assigns that string to `iframeSrcDoc`, starts an SSE/poll wait, and returns without an HTTP launch response. The rendered `srcDoc` iframe is the current same-origin preview. The connected implementation should replace the Execute button behavior with:

```json
POST /api/workshop/csrf/browser-attempt
{
  "tab": "post",
  "objectiveId": "csrf_p1",
  "html": "<the exact current editor contents>"
}
```

The response should use the workshop's existing fields: `success`, `blocked`, `victimState`, `newlyCompleted`, `judgments` and `projectionPending`, with a bounded non-secret browser observation for learner explanation. The component already has `showJudgments`, guarded victim/progress setters, SSE messages and polling reconciliation; reuse those rather than adding another progress channel. Disable only the Execute control while the attempt is active. Copy, Download and Execute in new tab can remain available as explicitly ungraded practice paths. The selected objective must still be cleared or replaced when live instructor visibility hides it; the server repeats that visibility check at admission.

## Minimum connected qualification

The decisive test is a complete request path, rather than another supplied DTO test:

- Authenticate the learner, submit the real launch request, execute the exact learner HTML at the configured same-site but cross-origin attacker origin, reach the production `/agent-action`, observe the isolated ambient cookie, obtain a real sandbox delta or 403, run the actual Judge, and verify durable completion.
- In vulnerable mode, require exactly one effect and the expected state change. In fixed mode, require a real token rejection, HTTP 403 and no state change. SameSite metadata alone cannot establish the defense because both origins are same-site.
- Repeat the request with curl-equivalent HTTP and copied browser headers. The intentional sink may mutate, but no browser receipt or objective credit may be created.
- Attempt a second request with the same managed cookie, a cross-owner request, a changed payload, and a stale generation. Each must fail without another effect.
- Reset while the browser is awaiting or dispatching. The launch must return the existing reset-invalidated response, no late receipt or completion may publish, and the page/context and registry entry must be gone before reset reports success.
- Verify the assembled React component sends the exact current editor value and selected visible objective, shows Judge feedback, reconciles victim/progress state, and cannot launch a hidden objective.

The already passing Chrome policy fixture establishes only that different ports on one hostname carry the deliberate Lax cookie. The connected gate must use the production route, observer, state store and Judge. Local qualification can use the frontend/backend port boundary. Hosted qualification remains open until both explicit origins are routable in that profile without deriving authority from request headers.
