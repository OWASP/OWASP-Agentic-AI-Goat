# Bound SecureShop user administration — proposed, 2026-09-19

Status: source review only. No schema, runtime, installed data or teaching sink changed. This design does not qualify the currently unsupported bound Users mutations.

## Current evidence and conflicts

- `server/routes/secureshop/boundGateway.js:504` exposes launch-bound GET `/admin/users`; it does not expose the three mutations. The legacy PostgreSQL admin router delegates those mutations to global user-management tools. Mounting that router would defeat launch isolation.
- `secureshopBoundAdmin.js:15` lists the three immutable templates, projects account profiles and explicitly returns `banned_at:null`. Both directory and other admin authorization compare the actor with a template whose role is admin. This must become effective-persona authorization, not merely a new mutation endpoint.
- `secureshopBoundPersonaAuth.js` hardcodes username→role in login, authenticate and API-key paths. `changePassword` derives username from the current role. A role overlay without replacing these assumptions would either prevent login after promotion or select the wrong credential. Resolve credentials by immutable persona ID/username, never reverse-map mutable role.
- `secureshopBoundPersonaRepository.js:148` reads template role plus a scoped password overlay; `readPersona` and `listPersonas` have no scope. API-key authentication also reads template role. Session authentication currently compares JWT role with persisted session role and credential version. Ban is checked by login, but the credential query does not currently return an effective ban.
- `secureshopBoundAccount.js:17` compares supplied role to the unscoped template before preparing a target. This would reject a legitimately changed role. Template enumeration remains useful for fixed fixture ownership (for example `secureshopPersonaInboxComposition`); do not globally change template APIs to mean effective roles.
- `secureshopConversationBinding.js` includes role in the immutable seven-field binding. Migration `0005_conversation_binding.sql` forbids rewriting it; `0014_secureshop_bound_session_inventory.sql` similarly freezes session identity/role. Preserve these historical identities. A role change requires new authentication and new conversation admission, not modification of old rows.
- `0015_secureshop_bound_password_overlay.sql` already supplies scoped credentials, credential-version checks and retirement cleanup receipts. Self-service password change intentionally retains/rebinds the requesting session. Admin reset must instead revoke every target session and must not reuse that method unchanged.
- `0016_secureshop_bound_api_keys.sql` supplies scoped keys and retirement cleanup. Revoking only bearer sessions would leave an alternate credential active. Ban/role transition/password-reset policy must cover keys explicitly.
- `0020_secureshop_bound_audit_events.sql` provides transaction-local store audit with actor, target, source and owner-deletion receipts. Existing persona audit helper derives the actor from the target template: unsuitable for an admin modifying somebody else. Supply authenticated actor separately; do not log passwords, hashes, bearer tokens or API keys.
- `docs/secureshop/VULNERABILITIES.md` retains intentional `llm06-excessive-agency`, credential-disclosure and related agent sinks. `agent-host/agents/user-management/tools/index.js` deliberately omits normal agent-side authorization. Secure REST administration and any future vulnerable model tool must be separate adapters over owned effects; do not harden or globally mount the legacy tool.

## Smallest coherent implementation

Keep the existing three persona templates and all global commerce users unchanged. Add one forward migration in `secureshop_agents` (next number must be reserved at implementation; current inspected head is0022). No new database or AWS assets.

1. Add a launch-owned persona state overlay keyed by the existing complete launch/scenario/generation/platform-owner/platform-session/persona-ID tuple. Store `effective_role`, `banned_at`, optional bounded reason, and monotonic `authority_version`. Missing row means immutable template defaults. Distinguish template role/fixture ownership from effective authorization role. Do not require effective roles to remain unique.
2. Add immutable administration operation receipts keyed by full scope and client operation UUID, binding actor ID, target ID, action, exact nonsecret request digest and expected authority version. Duplicate exact operation returns its original result; conflicting payload rejects; completed replay never re-applies to newer state. Retired scope rejects authority even if historical receipt exists. Password material must not enter the receipt digest in guessable plaintext form.
3. Expose `readEffectivePersona(scope,id)` and `listEffectivePersonas(scope)` while retaining template-only APIs for fixed artifact mapping. Add a transactional admin repository accepting server-resolved actor/session identity, target ID, expected version and operation UUID. Under the existing launch admission lock, revalidate active actor session and its effective admin role, current target version and retirement/deletion markers; mutate overlay/credential, revoke target credentials and append exact actor/target audit in the same transaction. Validate current platform launch outside/around the local transaction using established launch authority; do not imply cross-database atomicity.
4. Role change revokes all target sessions and keys. Old JWT role claims never gain new privilege; next login issues a fresh role-bound session. Ban rejects login, renewal, bearer and API-key authentication and revokes active credentials. Admin password reset installs a new bcrypt hash, advances credential version, revokes all sessions and keys. Bcrypt work occurs outside the lock with credential/state CAS inside. For the smallest reliable retry contract, accept an administrator-entered replacement password, return no plaintext, and persist a keyed request fingerprint for same-ID replay. If the existing UI requires generated one-time passwords, encrypted receipt-backed recovery or an explicit reset-token protocol is a separate prerequisite; never regenerate a different secret on retry or cache it only in RAM.
5. Update login/session creation/renewal/API-key authentication and scoped profile/directory/admin authorization to consult effective state. Add authority-version checks at each real mutation/tool effect boundary, not only HTTP authentication: a model run admitted before ban/demotion must fail before its subsequent effect. Revoke/close or fence old conversations while preserving immutable bindings and traces. Do not let an old customer conversation become an admin conversation. Existing purpose-specific resources may remain role-bound; inventory target allocation and uniqueness before allowing a new role to create a new target, preserving old owned data until explicit lifecycle cleanup.
6. Preserve platform ownership independently of the shop persona. Even a vulnerable shop promotion must not create platform admin permissions or alter another learner's launch. Self-ban/demotion can be allowed as a deliberate shop action with immediate sign-out and an explicit owner-level reset recovery path; do not silently protect the last shop admin by changing teaching semantics.

## File ownership and HTTP contract

- New `secureshopBoundUserAdministration` service and `secureshopBoundUserAdministrationRepository`; new forward migration and readiness checks. Reuse agents-store audit transaction API and existing scoped credential tables.
- `secureshopBoundPersonaRepository` / `secureshopBoundPersonaAuth`: effective-state and authority-version checks; stable ID credential lookup; session/key revocation. `secureshopBoundAccount` and `secureshopBoundAdmin`: scoped effective reads, correct actor authorization, projected bans/roles.
- `boundGateway`: only mount `/admin/users/:id/role`, `/ban`, `/reset-password` through verified launch + current bound persona admin checks. Require operation UUID and expected target version. Strict field validation and exact echoed acknowledgements; no scope/actor/owner accepted from body.
- `secureshopBoundReviewComposition`: construct/inject the service and make readiness verify the migration/permissions. Review all downstream authority caches and long-running effect admissions before enabling mutations.
- Existing Users UI: keep layout, add truthful unsupported/pending/conflict/re-authentication states and stable operation ID for an exact pending request. Authoritative GET after ambiguous outcomes; never display success merely because HTTP200 returned.

## Reset and deletion

Use the same launch retirement lock/order as conversation admission. Extend retirement to erase persona-state and password/key material, revoke sessions and retain immutable nonsecret operation/audit cleanup receipts. Never update templates. Retry must target the original retired generation and must not erase a new launch. Canonical student deletion must cover overlays and operation records under its existing owner/job authority, with a deletion receipt preventing late writes; audit retention/erasure follows the existing bound-audit owner-deletion policy rather than inventing permanent personal-data retention. Add explicit lifecycle capability/readiness coverage before exposing the UI.

## Required gates

- Unit contract: all role transitions, ID-based credential lookup after promotion, banned login/renew/key denial, exact replay/conflict, malformed acknowledgements, lost response recovery and self-demotion sign-out.
- Disposable PostgreSQL: fresh/populated/second-run migration; minimum runtime grants; immutable templates/history; concurrent login vs ban, password reset vs self-change, demotion vs effect, reset/deletion vs delayed publication. Prove active tokens and keys invalid, same-launch target changes real, sibling launch/owner untouched, cleanup and replay exact.
- Mounted canonical routes: customer/merchant/forged/stale actor denied; legitimate launch-admin changes owned persona only; all three mutations reflected in GET/profile/login, with audit actor distinct from target. Negative service-direct calls must not bypass current session checks.
- Actual agent qualification remains separate: an LLM06 promotion is only authentic when a real model selects the owned vulnerable tool, effect changes effective authority and independent Judge uses private effect evidence. Ordinary admin mutation never earns exploitation credit.
- Render existing Users/account pages and reset recovery; verify admin/student catalog totals only if curriculum capability/objective visibility changes. Do not advertise supported mutation before all authority and lifecycle consumers pass.

## Existing Users UI compatibility detail

`Users.jsx` includes legacy `banned` in its role dropdown. It is not a fourth effective role: retain the visible choice if desired but dispatch the separate ban operation, with its own operation ID/revision and explicit acknowledgement. Reject `set_role('banned')`; do not silently enable a backend operation by widening the role enum. The current UI has no unban control, so this foundation has no unban contract. Render banned status independently of the retained effective role. Global lookup credential snippets absent from bound profile results must remain unavailable, not invented from template defaults or copied from another launch. Any deliberately vulnerable credential-disclosure exercise needs its own owned tool/evidence qualification.

## Pending Users error-state integration

Current `Users.jsx` treats an unsuccessful/malformed users GET as an empty list and its mutation paths do not consistently catch request/JSON failures. A supported bound integration must distinguish unavailable from a verified empty directory, disable dependent actions until authority/data are current, catch errors without unhandled rejections, and reconcile uncertain mutations using the original operation ID and authoritative reads. This is documented work, not a UI change in the candidate foundation.
