# SecureShop bound commerce capability design — 2026-09-18

R48 proves the ten canonical rendered attack objectives. It does not prove the commerce and administrator paths used by the current UI. When the launch header is present, `server/routes/secureshop/boundGateway.js:168-240` owns the request and returns a terminal 503 for every path it does not mount, so the existing PostgreSQL customer and merchant handlers cannot provide those capabilities through the bound run.

The concrete route-to-handler, store and intentional-sink map is recorded in [the companion JSON](../../tasks/secureshop-bound-commerce-capability-map-2026-09-18.json). The first implementation slice should bind customer catalog helpers, reviews, cart and orders through the existing `secureshopCustomerRepository`, deriving the user from the authenticated launch-bound persona and checking resource ownership. Merchant review, listing, inventory, pricing and analytics should follow through `secureshopMerchantRepository` with retailer ownership and generation-bound agent sessions. Administrator controls, deletion and refunds need a separate adapter and acceptance cohort because they change lifecycle and authority boundaries.

The adapter must keep `req.ssLaunch` and `req.boundPersona` in every operation, use the dedicated `SECURESHOP` PostgreSQL store, and preserve transactional cart/order/outbox behavior. Existing teaching sinks remain intact: stored-review XSS and coupon SQL injection stay tagged and scoped to their intended routes; the generated vulnerability map remains authoritative. Each slice needs stale-launch, wrong-persona, cross-owner, reset/replay and sibling-isolation tests before it is included in a rendered qualification.

The request persona id cannot serve as the commerce owner. `boundGateway.js:101-104` exposes `req.boundPersona` from one of three canonical shared shop-user templates, while `createLaunchScope` carries the launch, scenario, generation and platform owner/session coordinates. The existing `secureshop_agents.bound_persona_sessions` mapping binds those coordinates to the template shop-user id. A new adapter must resolve that active mapping on every request and use the full composite binding as the owner key. Otherwise two learner launches would share carts, orders and merchant mutations through the same seeded user id.

Mutable commerce state should therefore use launch-scoped rows or reviewed binding columns keyed by `(launch_id, scenario_id, generation, platform_owner_id, platform_session_id, shop_user_id, role)`. Shared products can remain read-only; learner listing changes need launch-scoped overrides or clones. Reset retires only the exact binding generation, and a later generation must not read its predecessor's state. The existing `bound_persona_sessions` row is the admission mapping, not a substitute for per-launch commerce ownership.
