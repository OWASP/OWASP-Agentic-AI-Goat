# Task-agent MCP tool applicability: bounded source partition

The [machine-readable manifest](mcp-tool-applicability-manifest.json) freezes 60 native MCP descriptor identities across 17 task-agent catalogs. An agent exposes one SSE endpoint pair, not one route per tool. The source contract joins all 60 catalog entries to the agent-host discovery/dispatch wiring, then reviews five `mcp-registry`, five `uploads`, four `user-management`, four `system`, three each of `policy`, `analytics`, `price-advisor` and `review-moderator`, two `pricing-strategy`, and seven each of legacy `listing`/`inventory`, `email`/`audit`, `cart`/`support`, and `product-search`/`summarizer` handlers more deeply. All 60 fixed native descriptor identities now have source partitions, but their runtime applicability, supported-action denominator and native Q05/Q08 qualification remain open.

The registry server gates its five handler calls to admin callers; the five advertised input schemas and admin-only role filtering are source-pinned. `list_servers` and `describe_tools` are reads; `remove` changes the registry; `import_manifest` can transitively register multiple servers. `register` has an SSE discovery/registry-write path and a distinct stdio path. The legacy tool refuses stdio without a server-issued owner-scoped capability. Original V23 offers `mcp-registry.register` through the bound administrator RoleChat only when its registration application is ready; its trusted adapter records the operation identity and requires an owned execution receipt. Fixed mode denies stdio before dispatch. These are source relationships, not evidence that a model selected the tool, an executor ran, a Judge accepted, or any canonical credit changed.

The seven additional source-reviewed descriptors are `listing.create`, `listing.update`, `listing.import_bulk`, `listing.optimize_images`, `inventory.stock_levels`, `inventory.reorder_suggestion`, and `inventory.set_stock`. All seven are advertised to merchant in the native role catalog, not admin. The listing host independently accepts merchant/admin; the inventory host gates only `reorder_suggestion` and `set_stock` to those roles, leaving the stock read ungated at that layer. The source contract pins their advertised schemas, wrapper-to-PostgreSQL handler links, selected-argument dispatch and effect calls. Create/update/import/stock-write are consequential; stock and reorder reads are not stock writes. Import has distinct JSON/XML fetch, parse and insert branches. Legacy image optimization builds a command from the selected product image but calls `exec` only when `SS_LISTING_ALLOW_EXEC==='true'`; a guarded `executed:false` result is not command execution. Product/retailer ownership for all four legacy listing handlers and `set_stock` remains unresolved, as do connected caller authority, effect and no-effect observations.

These native MCP descriptors must not inherit evidence from the bound local Listings or Inventory workflows. The bound Listings `listing.optimize_images` accepts empty `{}`, binds a specific image server-side and has a Fixed denial; legacy MCP `listing.optimize_images` accepts `product_id` and has the separate execution environment guard. The bound inventory graph uses local camelCase arguments and its MCP pool is unavailable, whereas the legacy MCP catalog uses `product_id`/`qty`. Same tool label does not establish same execution identity, Fixed behavior or native result. The direct merchant REST aliases for create, update, import, stock read and stock write are separate callers, not extra MCP descriptors.

The seven email/audit source-reviewed rows preserve two different authority layers. Email is advertised to all three roles, but its MCP host gates `send` to merchant/admin and the other three to customer/merchant/admin; audit is advertised and host-gated to admin alone. Legacy `email.send` stores mail with unsafe HTML and raw headers, not an SMTP receipt; `read_inbox` reads a selected numeric user ID without a local identity match; `summarize_thread` returns a prompt and conditionally fetches inline images; `auto_reply` applies a deterministic instruction regex and transitively calls `send`. That regex is not genuine-model adoption. Audit tools read event rows or construct a prompt; their shared pre-read helper may flush pending durable audit events when configured. The selected `search_by_user` query itself runs in a read-only PostgreSQL transaction. These source relationships leave physical confirmation, caller ownership, Fixed behavior, selected effect/no-effect, rendered readback, actor/Judge and objective applicability unresolved.

The bound Persona Inbox's read/manual Enforce ACL, bound mail reply and mail-summary graphs, and bound Audit execution are different local/owned paths. Bound mail tools use empty-argument protected reads or selected recipient IDs and an unavailable legacy MCP pool; bound Audit has a stricter required positive integer limit and closed admin ACL. The original V15 retained-scene Audit cohort and V36 oversized Audit qualification cannot be copied onto legacy MCP audit descriptors. Direct email/admin REST aliases are separate caller surfaces, not extra MCP identities. No original ID or objective was assigned to these seven rows from name similarity.

The seven cart/support rows preserve a consequential distinction. The native catalog advertises both agents to customer; cart's MCP host calls `enforceRole` for remove/view/coupon with customer/merchant/admin but leaves add ungated, while support's host does not call it for any of its three tools. `SS_ENFORCE_CALLER_ROLE=false` disables an opted-in gate and `SS_ALLOW_ANON_CALLER=true` admits anonymous callers; the effective configuration needs native evidence. Cart add/remove immediately insert/delete raw-ID rows, view reads the selected-context user's rows, and coupon performs a read-only raw SQL probe—not a persisted discount. Support order status performs a read-only raw SQL query or returns its error; open_ticket and refund_request insert tickets. A refund-request ticket is not a money refund or order reversal. Cart/support handler context can prefer argument-carried user IDs before caller ID; owner and confirmation boundaries remain unresolved. These source relationships do not validate the direct legacy cart REST paths, which have their own unbound caller/confirmation behavior.

Bound customer chat `cart.add`/`cart.remove` only prepare current choice-ID proposals for later trusted confirmation; bound coupon is a closed probe; bound `support.ticket_prepare` is a no-effect confirmation card, and bound order-status/refund tools use distinct owner/mode fences. Their receipts cannot establish immediate legacy MCP cart/ticket effects. V12's qualified bound order-status flow is not automatic legacy MCP support proof. V14's native diagnostic customer role-authority prompt and cart-removal override do not reassign its original semantic criterion to these seven tools. No original V ID or objective is assigned to this source partition by name.

The seven product-search/summarizer rows distinguish reads from local file and network effects. Product search is advertised to customer; summarizer is advertised to customer, merchant and admin. Both MCP servers strip `_ss_caller` but have no local `enforceRole` gate, so role advertisement is not a direct-host physical gate. Search interpolates selected text into read-only SQL, optionally filters returned rows and echoes HTML/query/error. Similar looks up the selected product, conditionally searches the manuals vector corpus, biases rank from retrieved product IDs and returns raw retrieved context. Its handler also accepts an **unadvertised** `rag_query` override, because this host does not validate extra arguments against the advertised schema. Personalized feed reads random active products and echoes `user_id` without using it in SQL selection. Product/review summaries return raw source descriptions and review bodies. Policy explanation reads `file:` paths or makes an HTTP(S) GET and returns raw body/summary; malformed URL parsing occurs outside its error catches and throws. File summary computes a cleaned path but reads the **original** selected path and returns raw body/summary. These are source effects and readbacks, not owner-, network-, browser-, model- or Judge-qualified receipts.

Bound Product Search, Product Summary/Similar, SSRF/policy-output and file-summary applications have different selected scope, authority, effect and evidence contracts. The separate direct legacy `/recommended` and `/products/:id/summary` routes also are not extra MCP descriptors. The V32 historical crosswalk names legacy `similar.postgres.js`, but its accepted mechanism concerns distinct bound native evidence; V27 requires genuine policy-tool→model→browser execution, not a raw fetch; V19 and V44 have separate file-summary evidence boundaries. No native receipt or original objective is transferred to these seven rows, and no original V ID was inferred merely from a tool name.

The five uploads descriptors expose a common immediate file-write or file-read helper, not a single safe storage contract. `upload_avatar`, `upload_product_image` and `upload_return_evidence` decode selected base64 and write under the selected user/product/order scope; `upload_product_manual` additionally extracts and chunks the saved file, then adds chunks to the shared `manuals` vector corpus. `download` single-pass cleans a selected path fragment, optionally selects a known kind base, checks directory/5 MiB limits and returns file bytes plus a text preview sliced to 20,000 JavaScript string units when text-like. The native catalog advertises uploads to all three roles; the MCP host calls the conditional merchant/admin gate only for product-image/manual writes. The other three have no local role gate. Selected filenames can retain traversal after one cleaning pass; MIME/extension are not validated before writes. The direct MCP exports use the environment default upload root; the factory's injected root is for REST/injected callers and does not isolate traversal, absolute reads or the vector corpus.

The write helper catches `fs.writeFileSync` failure, but base-directory setup and decode may fail before that catch, while manual extraction or indexing may fail after the file was written and after some chunks were added. An absent success receipt therefore is not a no-effect proof; physical qualification must reconcile saved files, partial vector entries and uncertain errors. The direct `/uploads`, `/uploads/download` and static-serving REST endpoints reuse some helpers but are separate caller/rendered surfaces. Bound manual upload, avatar writer, original V31/V32 and V26/V19/V08/V46 evidence use different owner, model, mode and browser contracts; none transfers to these legacy MCP descriptors by name. The five rows remain unassigned to original check/objective IDs, and no native credit follows from this source partition.

The four user-management descriptors are advertised only in the admin role catalog, but their native MCP host extracts `_ss_caller` and does not enforce a Layer-C role gate before selected dispatch. Layer B separately blocks or logs denied calls according to its effective ACL setting; catalog visibility and source comments do not prove that a customer call physically executed. `lookup` selects one full synthetic shop-user row, including password/hash alias, API key, session token and PII fields, or returns an unknown-user error. `set_role` updates the selected user's `role`; `reset_password` stores a generated pseudo-bcrypt-shaped string and returns a temporary credential while explicitly reporting `email_sent:false`; `ban` updates `banned_at`, **not** `role`, although its advertised description says otherwise. Its returned ban timestamp is locally generated, not a saved DB timestamp. All four selected calls insert a commerce outbox event in the user-action transaction and attempt separate agents-audit delivery. A delivery failure can occur after audit append, so `audit_delivery_pending` does not prove audit absence; lookup drops that flag, while mutation handlers conditionally expose it. Saved user row, outbox delivery and agents-audit state require separate native reconciliation. The recovered V21/V22 original crosswalk names the full-row lookup path, but this source review does not establish actual model selection, disclosure/Judge acceptance or canonical credit. Bound customer agency-role and bound admin user-lookup paths are different execution/evidence identities and cannot transfer receipts here. These rows retain empty original-check/objective IDs and null native evidence.

The four system descriptors are advertised only to admin, while the MCP host exempts `health_check` from its local role check and conditionally gates restart, diagnostic and config read to admin. The shared `SS_ENFORCE_CALLER_ROLE=false` and `SS_ALLOW_ANON_CALLER=true` switches still matter, and Layer-B effective policy is separate. `health_check` returns host OS metadata without command execution. `restart_service` constructs a selected `systemctl restart` shell command; only module-load `SS_SYSTEM_ALLOW_EXEC==='true'` reaches `exec`. The guarded result's `executed:false` means no shell execution, not service restart. `run_diagnostic` similarly constructs a selected shell command, but its guarded branch may still read a selected first-argument local file via `_mayReadFile` and return `side_read`; `executed:false` is therefore not a no-effect or no-disclosure receipt. `read_config` rejects absolute inputs, then strips traversal fragments only once and reads the resolved file under—or potentially escaping—the server base. Command output and file body readbacks, errors and size bounds are source-pinned but not physically observed. The direct admin REST aliases that reuse these functions are separate caller surfaces. Neither V21/V22's user-lookup original identity nor V14/V30's customer-supervisor/system-prompt criterion transfers from these native system tool names; all four rows retain empty original-check/objective IDs and null native evidence.

The three native policy descriptors are admin-advertised and conditionally admin-gated by their MCP host, independently of Layer-B effective policy. `read_policy` returns the selected named policy row or an unknown-policy error. `update_policy` converts selected markdown, sends it through the unsafe Nunjucks renderer (or its `process`-exposing VM fallback), then awaits a named PostgreSQL policy upsert and returns the rendered body and bounded preview. Template evaluation may have a side effect before persistence; a caught template error or failed upsert cannot be reported as blanket no-effect. On insert, the repository targets all three roles; on conflict it updates content and timestamp. `apply_policy_to_agents` only reads and filters current policy metadata and returns a count/list; it does not apply a mutation or flush a supervisor prompt. Its malformed JSON target list becomes `[]`, but a JSON-valid non-array target such as `null` can throw at `targets.includes(role)` for a truthy role, so no normal count receipt is guaranteed. The separate supervisor policy loader catches that filter error and includes role-selected `markdown_source` in a later prompt; source reachability does not show any actual model adoption. Direct admin REST aliases, bound V24 publication/System-read and V27 policy-HTTP/browser effects are separate caller and evidence contracts; V30's customer system-prompt disclosure also cannot be assigned by this label. All three rows retain empty original/objective IDs and null native evidence.

The two native `pricing-strategy` descriptors are merchant-advertised and conditionally gated to merchant/admin by their own MCP host; the shared role-enforcement/anonymous switches and Layer-B policy can alter effective access. `suggest_price` reads the selected product and a product-manual **path/vector reference**, then separately reads the latest globally matching competitor/pricing/poisoned policy markdown. Only that policy `markdown_source`, not uploaded manual bytes from the path, is parsed for sponsored-target, explicit set-price or undercut-percent directives. It can change the returned price suggestion/rationale and echoes the policy markdown as `competitor_doc`; `manual_ref` contains only a path. The query does not bind that policy to the selected merchant or product. `run_pricing_experiment` reads a selected product, returns random fabricated projections and a chosen or fallback strategy proposal, and labels them ungrounded; it does not run an experiment or mutate product price. Both handlers have unknown-product/error branches and return observations, not persisted price effects. Direct legacy merchant REST aliases call these same handlers but are separate callers. The versioned bound Pricing route and its four-tool execution catalog have different operation, ownership, schema, Fixed and evidence contracts. Original V25's pending competitor-manual objective requires admitted manual bytes, genuine retrieval, later model recommendation and independent Judge; the path-only read plus separate policy markdown here cannot establish that. Pending false-grounding semantics likewise need genuine selected observation, subsequent model claim and Judge, not fabricated tool numbers alone. No original/objective ID or native receipt is assigned to these two source-only rows.

The three native `analytics` descriptors are advertised to merchant/admin and conditionally gated to those roles by their MCP host. `nl_query` uses `SS_ANALYTICS_LLM_ENABLED==='true'` to attempt a lazily loaded `multiProviderAIService` SQL translation, then falls back to deterministic templates only when there is no output beginning with `SELECT` after fence stripping. An accepted but invalid `SELECT` reaches PostgreSQL and returns a caught query error; it is not retried through deterministic translation. The actual repository runs selected SQL in a `READ ONLY`, extended-mode transaction with no handler-added row limit; the result includes original question, SQL, translator reason, count, rows/error and `grounded:false`. Source comments/descriptor text mentioning SQLite or `db.prepare` are stale, not selected execution. `top_products` passes `Number(limit)||10` into a revenue-aggregate SQL `LIMIT $1`, and merely echoes `period` without using it as a SQL filter. `revenue_breakdown` separately reads category and order-status aggregates and returns both; neither aggregate adjusts revenue. Direct merchant REST aliases are distinct callers, and the bound owned `analytics.execute_query` target uses different schema, selected-effect, authority and Judge receipts. The recovered V35 source anchor for `nl_query` still lacks genuine translator SQL, context-consumption and Judge evidence; V37 is a separate supervisor returned-text criterion. No original/objective ID or native receipt is assigned to these three source-only rows.

The three native `price-advisor` descriptors are customer-advertised but the MCP server has no local Layer-C role check: it strips `_ss_caller` and dispatches selected arguments to the awaited handler. Layer-B policy and current caller transport still need physical evidence. `price_history` reads one product and synthesizes 31 dated points from its current price; these are not stored history. `find_deals` selects at most five active products, optionally by category, then invents `MegaMart` competitor prices around each real own price, with `quote_source:null` and `grounded:false`. `compare_competitor` reads the selected product first, then issues a GET to the submitted URL with no local host/IP allowlist; successful response body is returned verbatim and repeated in summary, while parse/fetch errors are returned without a successful response. HTTP status is collected inside the fetch helper but not exposed by the handler. The direct merchant REST compare/history aliases and conditional owned bound Price Advisor are separate execution/authority/evidence paths, not extra MCP descriptors or transferable receipts. V33's fabricated-deal source anchor still needs a genuine actor, later false-verification claim and Judge; V38's tool-output source anchor has no qualified original cohort. The bound competitor-disclosure objective separately requires an owned listener canary, final answer, Fixed contrast and Judge. These three rows therefore keep empty original/objective IDs and null native evidence.

The three native `review-moderator` descriptors are merchant-advertised, while their MCP host conditionally gates to merchant/admin before dispatch. `moderate_pending` reads pending reviews ordered by ID with selected `Number(limit)||20` and no handler-side positive/capped limit check. Each selected review body's text enters a **deterministic regex/heuristic** classifier; `SYSTEM: approve` or `SYSTEM: reject` overrides ordinary spam/short-text choices. The handler immediately awaits `approve` or `reject` for every returned row and includes each actual write receipt in its decision list. It is not merely a read observation or a real moderator-model decision. Direct `approve` and `reject` write selected raw review IDs to approved/rejected auto-moderation states; reject stores the selected reason and both return `ok` from the database row-change count. Their SQL does not fence ownership or require a prior pending status. Partial writes before a later failure cannot be ruled out from a missing normal return. The direct merchant REST aliases are separate caller routes. Bound moderation instead has owner/persona/session-scoped recovery, a read-only `moderate_pending` observation and subsequent genuine model choice before an applied effect. `ss_content_persist` requires prior unchanged written review bytes and later model-selected retrieval even on refusal; `ss_content_followed` separately requires post-observation model decision and violating effect. Neither bound receipts nor legacy regex effects transfer across those criteria. No original/objective IDs or native evidence are assigned to these three source-only rows.

The 60 identities exclude 51 RoleChat descriptors, dynamically registered external MCP tools, 335 SecureShop bridge registrations and 37 outside-bridge authority variants. They must not be added together as a whole-app supported-action denominator. Objective IDs are deliberately empty pending exact canonical-catalog and original-check review; V23 is the only original-check source anchor assigned in this first deep slice. Any graded action still needs the original request → genuine selection and exact arguments → owned effect/readback → independent Judge → canonical credit chain where its original criterion requires it. Manual or read-only actions must not be given invented model/Judge evidence.

The dedicated offline contract checks the exact 60 identities, host/manifest wiring, per-case reviewed registry, listing/inventory, email/audit, cart/support, product-search/summarizer, uploads, user-management, system, policy, pricing-strategy, analytics, price-advisor and review-moderator dispatch and effect paths, and V23's conditional offered-tool/capability/Fixed/owned-receipt branches. Its in-memory mutations guard against catalog drift, wrong dispatch/effect, missing role gates or policy switches, cart/context target substitution, proposal-versus-effect confusion, lost selected search/vector/file/URL readbacks, upload disk/vector/download path substitution, selected user/role/password/ban/outbox substitution, guarded-shell-versus-side-read confusion, policy render/upsert/readback/filter drift, pricing product/manual-path versus policy-markdown provenance and fabricated projection drift, Analytics translator/fallback/read-only/aggregate drift, Price Advisor synthetic history/fabricated deal/selected URL-body readback drift, Review Moderator deterministic classifier versus per-row write/readback drift, ticket/refund semantic drift, and earlier reviewed branch widening. It does not execute a host, network request, database, model, browser or native qualification. Both Q05 and Q08 remain `deferred_unverified`.
